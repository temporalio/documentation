These measurements provide starting points for [capacity planning](/production-deployment/temporal-proxy/operate).
They are not performance guarantees. Payload size alone reduced throughput by more than half in the reference tests.
Re-measure with your workload and the proxy version you deploy.

## Check the test conditions

All throughput ceilings used:

- One Temporal Proxy replica, with CPU request and limit of 4, a memory limit of `12Gi`,
  `GOMEMLIMIT=11GiB`, and `connection.maxConnections: 32`.
- AWS Graviton arm64 nodes from the c6g family. Performance on x86 nodes was not measured.
- Mutual TLS on both the Client-to-proxy and proxy-to-Cloud connections.
- A Temporal Cloud upstream with Namespace rate limits raised so they did not cap throughput.
- The `throughput_stress` workload from [omes](https://github.com/temporalio/omes), with 20 to 200 Go SDK Workers.
  Payloads contained random bytes, making gzip inexpensive. Compressible payloads can cost more CPU.
- An unspecified pre-release proxy build. The source test report does not identify its version or commit, so these
  results cannot establish performance for a specific released version.

Two-CPU and eight-CPU capacity figures, and fleet-sizing examples, are extrapolated from these tests. A multi-replica
capacity soak was not performed. A separate rollout test observed load distribution across two replicas.

## Compare throughput and memory

| Workload | Measured throughput ceiling | CPU cores per 1,000 requests per second |
| --- | --- | --- |
| Small payloads, no encryption | About 12,900 requests per second sustained; peak 13,300 | 0.29 to 0.31 |
| Small payloads, encryption with a KMS extension at 5 ms latency and DEK cache enabled | About 10,500 to 11,400 requests per second | About 0.33; a controlled comparison at about 10,000 requests per second measured 0.35 to 0.36 |
| Encrypted payloads averaging about 900 KB, up to 1.9 MB | About 5,000 requests per second, CPU-bound | About 0.8 |

For small unencrypted payloads, throughput fell to about 12,200 requests per second past saturation. Encryption's CPU
overhead depended on the comparison: about 8% above a 0.305 baseline, 14% above a 0.29 baseline, and 14% to 17% in the
controlled comparison. KMS latency had no visible throughput effect with the DEK cache enabled. Disabling the cache
generated about 2,800 KMS calls per second and increased CPU per request by 22% relative to unencrypted traffic.

About 100 Workers per replica ran without observed capacity problems. At 200 Workers, CPU reached 3.98 cores and errors
rose during Client restarts. Worker counts describe this workload's concurrency, not a supported maximum.

| Condition | Measured RSS |
| --- | --- |
| About 10,000 to 11,000 requests per second, small encrypted payloads, 20 Workers, 65-hour soak | About 1 GiB, stable |
| About 12,000 to 13,000 requests per second, small payloads, 20 Workers | About 1.4 to 1.7 GiB |
| About 11,000 to 14,000 requests per second, 100 to 200 Workers | About 2.7 to 3.9 GiB |
| About 5,000 requests per second, payloads averaging 900 KB | About 5 to 7 GiB |
| Reconnect burst at about 10,000 requests per second with few Clients, a `2Gi` memory limit, and `GOMEMLIMIT=1700MiB` | Peak 1.65 GiB, no out-of-memory kill |

Only the last row used a memory limit below 12Gi. It does not validate lower limits with 100 or more Workers.

## Calculate fleet capacity

This table applies a 65% planning target to small-payload ceilings. The 4-CPU ceilings were measured; the other sizes
assume linear CPU scaling and require validation.

| Replica CPU | Unencrypted ceiling / at 65% | Encrypted ceiling / at 65%, using a 10,500-request ceiling |
| --- | --- | --- |
| 2, extrapolated | About 6,450 / 4,190 requests per second | About 5,250 / 3,410 requests per second |
| 4, measured ceiling | About 12,900 / 8,390 requests per second | About 10,500 / 6,830 requests per second |
| 8, extrapolated | About 25,800 / 16,770 requests per second | About 21,000 / 13,650 requests per second |

The following examples use 4-CPU replicas, a 65% normal-load target, one spare replica, and three equally populated
zones. The zone-loss count meets both the normal-load requirement and a maximum 75% utilization after losing a zone.
They assume even request distribution, which long-lived connections do not guarantee.

| Peak requests per second | Unencrypted: normal count / zone-loss count | Encrypted: normal count / zone-loss count |
| --- | --- | --- |
| 10,000 | 3 / 3; zone loss leaves 5,000 per pod, about 39% of ceiling | 3 / 3; about 48% after zone loss |
| 30,000 | 5 / 6; zone loss leaves 7,500 per pod, about 58% | 6 / 6; about 71% after zone loss |
| 100,000 | 13 / 18; zone loss leaves about 8,330 per pod, about 65% | 16 / 21; about 7,140 per pod, about 68% after zone loss |

For encrypted payloads averaging 900 KB, a peak of 15,000 requests per second and a 5,000-request ceiling give six
replicas for both calculations. Losing two replicas leaves 3,750 requests per second per pod, exactly 75% of the ceiling,
with no additional margin for skew.

Use the [sizing formulas](/production-deployment/temporal-proxy/operate#plan-the-replica-count) with your measured ceiling.
Do not treat these extrapolations as validated fleet capacity.

## Compare recovery behavior

| Test event | Observation |
| --- | --- |
| Proxy pod deletion or eviction | The replacement reached 85% to 100% of steady throughput within its first minute and steady throughput in about two to five minutes. Errors stayed below 1%. |
| All Clients restarted together | Throughput fell to 69% to 86% of steady for about one minute and recovered in about three to seven minutes. At 200 Workers with saturated CPU, one `Unavailable` burst reached 3.7%. |
| 65-hour encrypted soak at about 10,000 to 11,000 requests per second | Memory stayed near 1 GiB with no restarts. |
| Rolling deployment to two replicas | Requests split about 99.6% / 0.4% afterward, without Client rebalancing. |
| Rollout without a readiness probe | A crash-looping pod replaced a healthy pod, causing about 4.5 minutes of outage. A readiness probe that detects startup failure would prevent that replacement. |

Validate recovery with your deployment's connection behavior and failure scenarios. Follow
[Validate your deployment](/production-deployment/temporal-proxy/operate#validate-your-deployment) to repeat the
capacity and disruption tests.
