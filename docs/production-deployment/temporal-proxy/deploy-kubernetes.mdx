The [Helm chart](https://github.com/temporalio/helm-charts/tree/main/charts/temporal-proxy) provisions everything the
proxy needs: a Deployment, a Service, the ConfigMap that holds your configuration, a ServiceAccount, and an optional
HorizontalPodAutoscaler and PodDisruptionBudget. The `extraObjects` value renders additional manifests as-is, for
example an ExternalSecret that supplies upstream credentials.

**Recommended starting size:** For a Temporal Proxy instance that applies payload encryption for all payload sizes,
use **4 CPUs and 12 GiB of memory**, with `GOMEMLIMIT=11GiB`, and plan for each instance to handle up to
**3,000 requests per second and 100 SDK Workers**. Scale beyond these limits by adding more Proxy replicas (instances)
behind a gRPC-compatible load balancer. For more efficient sizing based on the features and payload sizes you use, see
[Sizing and performance](/production-deployment/temporal-proxy/sizing-and-performance).

## Supply the configuration

`config` mirrors the proxy's own configuration schema. Whatever you put under it is what lands in the ConfigMap the
chart mounts at `/etc/temporal-proxy/config.yaml`. The chart does not run `config` through Helm's `tpl` function, so the
proxy's own per-request templates, such as `{{ .RemoteNamespace }}` in an upstream `hostPort`, pass through untouched
and are evaluated by the proxy at request time.

```yaml
config:
  routing:
    default: default
  upstreams:
    - name: default
      hostPort: localhost:7233
```

If you leave `config.hostPort` unset, the chart defaults the gateway's listen address to `:<service.port>`.

Values the configuration references with `${VAR}` come from `env` and `envFrom` on the Deployment, which is how you
supply things like a Temporal Cloud account identifier:

```yaml
env:
  - name: TEMPORAL_ACCOUNT
    value: a1b2c

envFrom:
  - secretRef:
      name: proxy-env
```

## Supply credentials from a Secret

Two configuration fields accept either a plain string or a `secretKeyRef`, so the ConfigMap never has to hold a
credential in plaintext:

- `upstreams[].credentials.static.apiKey`
- `auth.staticToken.token`

Given a `secretKeyRef`, the chart adds an environment variable to the proxy container sourced from that Secret and
rewrites the configuration value to `${VAR}`, which the proxy expands at startup. The generated names are
`TP_UPSTREAM_<NAME>_API_KEY`, where `<NAME>` is the upstream's name upper-cased with non-alphanumeric characters
replaced by `_`, and `TP_AUTH_STATIC_TOKEN`.

```yaml
config:
  upstreams:
    - name: cloud
      hostPort: '{{ .RemoteNamespace }}.tmprl.cloud:7233'
      credentials:
        static:
          apiKey:
            secretKeyRef:
              name: temporal-cloud
              key: api-key
```

That renders `apiKey: ${TP_UPSTREAM_CLOUD_API_KEY}` into the ConfigMap and adds a matching environment variable backed
by the `temporal-cloud` Secret's `api-key` entry.

## Supply TLS material {/*#supply-tls-material*/}

The gateway's `config.tls` block and each `upstreams[].tls` block accept a `secretName`. The chart mounts that Secret at
`/etc/temporal-proxy/certs/gateway` or `/etc/temporal-proxy/certs/upstream-<name>` and fills in the file paths for you:

| Configuration key | Value                                                         |
| ----------------- | ------------------------------------------------------------- |
| `cert`            | `<mount>/tls.crt`, or `<mount>/<certKey>` if `certKey` is set |
| `key`             | `<mount>/tls.key`, or `<mount>/<keyKey>` if `keyKey` is set   |
| `ca`              | `<mount>/<caKey>`, only when `caKey` is set                   |

`ca` is opt-in because it changes behavior rather than just adding material. On the gateway, a `ca` enforces mutual TLS,
so only set `caKey` on `config.tls` when you intend to require client certificates. See
[Configure TLS](/production-deployment/temporal-proxy/configure#configure-tls) for what each combination means.

```yaml
config:
  tls:
    secretName: temporal-proxy-server-tls
  upstreams:
    - name: cloud
      hostPort: '{{ .RemoteNamespace }}.tmprl.cloud:7233'
      tls:
        secretName: temporal-cloud-client-tls
        caKey: ca.crt
```

The default keys match the `tls.crt` and `tls.key` pair [cert-manager](https://cert-manager.io/) issues, but
cert-manager is not required: any Secret works, and `certKey`, `keyKey`, and `caKey` point at whatever keys yours uses.
Keep upstream `name` values DNS-safe, meaning lowercase alphanumeric characters and `-`, since the chart builds a volume
name from them. To manage certificate files yourself instead, skip `secretName` and mount them with the chart's generic
`volumes` and `volumeMounts` values.

## Configure capacity

Set CPU and memory requests so Kubernetes reserves the capacity you used in your load test. Equal requests and limits
for both resources give the pod Guaranteed quality of service; a lower CPU request or no CPU limit allows bursts but
makes capacity depend on spare node CPU. Plan from the CPU request, not potential bursts.

This Helm values example applies the standard per-instance sizing. Add replicas for availability or additional
capacity using [Sizing and performance](/production-deployment/temporal-proxy/sizing-and-performance):

```yaml
replicaCount: 1
env:
  - name: GOMEMLIMIT
    value: '11GiB'
resources:
  requests:
    cpu: '4'
    memory: 12Gi
  limits:
    cpu: '4'
    memory: 12Gi
```

Use node allocatable CPU and memory, minus DaemonSet requests, when checking whether replicas fit. A four-CPU request
generally cannot fit on a four-vCPU node because some capacity is reserved for the system. Reserve an additional pod
slot if your rollout strategy uses a surge replica.

To tolerate zone loss, spread replicas across zones with `topologySpreadConstraints`, using
`topology.kubernetes.io/zone`, `maxSkew: 1`, and `whenUnsatisfiable: DoNotSchedule`. Match the selector to your release's
pod labels. The chart does not expose this field; add it with a post-renderer or manage the Deployment directly.

## Configure autoscaling

Size for peak traffic and use a HorizontalPodAutoscaler (HPA) as a safety net. New replicas receive new connections but
do not draw established connections away from a saturated replica. Average CPU can hide a hot pod, so monitor each pod.

Start with CPU utilization against the request, a 65% target, and a minimum replica count that meets your peak sizing.
Avoid memory-based scaling because resident set size (RSS) can stay high after traffic falls. These values work with chart 0.2.1:

```yaml
autoscaling:
  enabled: true
  minReplicas: 6
  maxReplicas: 12
  targetCPUUtilizationPercentage: 65
  targetMemoryUtilizationPercentage: null
```

Choose the replica bounds from your capacity plan and upstream limits. With `autoscaling.enabled: true`, the chart omits
Deployment `replicas`, so Helm upgrades do not reset the HPA's count. If you create an HPA yourself while that setting is
false, remove `replicas` with a post-renderer.

Scale down slowly, one pod at a time, because removing a loaded pod forces its Clients to reconnect. The chart source
on `main` supports `autoscaling.behavior`; chart 0.2.1 needs a post-renderer to add HPA behavior. If you need to
redistribute traffic, test and stagger Client reconnects rather than restarting all Clients together.

## Control rollouts and disruptions

Keep spare capacity during rolling upgrades. Use `maxSurge: 1` and `maxUnavailable: 0` when a node has room for a full
replacement pod. Use `maxSurge: 0` and `maxUnavailable: 1` only when your replica count includes a spare and no surge
slot is available. Both depend on readiness detecting a faulty replacement; a TCP probe cannot detect every failure.

The chart source on `main` exposes the following settings. Published chart 0.2.1 does not render `strategy`,
`minReadySeconds`, `terminationGracePeriodSeconds`, or `lifecycle`; add those fields through a post-renderer or manage
the Deployment directly. This example waits 30 seconds after readiness before continuing the rollout:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
minReadySeconds: 30
terminationGracePeriodSeconds: 60
lifecycle:
  preStop:
    sleep:
      seconds: 15
podDisruptionBudget:
  maxUnavailable: 1
```

A PodDisruptionBudget limits voluntary evictions such as node drains. It does not govern Deployment rollouts or prevent
node failures. Limit voluntary node disruption during busy periods: pod moves can cause several minutes of reconnects
and uneven traffic. Use your node autoscaler's disruption controls and validate pod-loss recovery under load.

For slow startup, add a TCP `startupProbe` through a post-renderer; the chart does not expose it. This delays liveness
checks during initialization but cannot make an unreachable dependency available.

### Probe the gateway

The chart passes `livenessProbe` and `readinessProbe` through to the container as written. Published chart 0.2.1 defaults
to HTTP GET probes, which the gRPC listener does not answer. The chart source on `main` uses TCP socket probes instead.
Override the probes in chart 0.2.1 with the following values. The named `http` port is the gateway's gRPC port despite
its name:

```yaml
livenessProbe:
  tcpSocket:
    port: http
  periodSeconds: 10
  failureThreshold: 6
readinessProbe:
  tcpSocket:
    port: http
  periodSeconds: 5
  failureThreshold: 2
```

The listener opens after startup dependencies have connected, so a TCP probe detects an uninitialized or stopped
process. It does not validate TLS certificates, upstream or KMS reachability after startup, or whether requests can
complete. Monitor those separately. Keep liveness independent of upstream and KMS availability so an outage does not
trigger repeated restarts.

For a plaintext gateway, a Kubernetes gRPC probe can also read the standard health service:

```yaml
livenessProbe:
  grpc:
    port: 8443 # Must be numeric. Match service.port.
readinessProbe:
  grpc:
    port: 8443
    service: temporal.api.workflowservice.v1.WorkflowService
```

Naming a service is optional; omit it to check the empty service name. Either way the answer is the same, because the
proxy's health is process-wide, and a service your configuration does not allow returns `NOT_FOUND`. See
[Health checks](/production-deployment/temporal-proxy/configure#health-checks) for what the gateway publishes.

The status your probe reads is refreshed by a check the proxy runs against itself every 30 seconds, tunable under the
`health` block. The two cover different scenarios, which is why you want both. The internal check exercises the
interceptor chain every forwarded request travels, and your probe proves the gateway still accepts a connection and
completes a handshake, which the internal check deliberately skips.

Kubernetes gRPC probes connect in plaintext, so they cannot reach a gateway that terminates TLS. When `config.tls` is
set, use a TCP probe for listener readiness and monitor successful TLS requests separately. The default scratch-based
image has no shell or probe executable, so an exec probe requires a custom image that supplies one.

### Shut down cleanly

On `SIGTERM` the proxy reports `NOT_SERVING` and drains in-flight RPCs. The gateway's default drain timeout is five
seconds, and the whole stop sequence is bounded at 30 seconds. Long-poll methods
block for much longer than that, so a rollout normally cuts some of them short: the proxy logs a warning naming the
deadline that ended the drain and still exits zero, because the callers re-poll. Treat that warning as ordinary on a
restart rather than a failed shutdown.

Allow time for Kubernetes to remove the pod from Service endpoints before shutdown. The rollout example uses a native
15-second `preStop` sleep and `terminationGracePeriodSeconds: 60`, covering the delay plus the proxy's shutdown budget.
The sleep handler is enabled by default in Kubernetes 1.30 and later; verify support before using it. The default image
has no `sleep` binary, so an exec hook that runs `sleep` does not work.

## Monitor the deployment

Configure your scraper to reach `/metrics` on `metrics.hostPort`, default `:9090`. The chart does not declare a metrics
container port or create a PodMonitor. See the [metric definitions](/production-deployment/temporal-proxy#observability)
and [capacity queries](/production-deployment/temporal-proxy/sizing-and-performance#measure-your-workload).

Monitor per-pod CPU, RSS, request rates, errors, and restarts. Investigate sustained CPU throttling or uneven traffic,
even when average utilization looks healthy. Watch KMS errors, cache misses, and DEK rotation when encryption is enabled.
A TCP probe cannot detect a pod that accepts connections but no longer completes requests.

During an upstream, KMS, or extension-server outage, avoid unnecessary restarts, evictions, and rollouts. Static
upstreams and extension servers must connect during startup; failure to open a configured KMS key also prevents
startup, including decrypt-only keys. Cloud KMS providers determine which checks occur when a key is opened. Running
pods can use cached DEKs for some requests, but rotation and cache misses still need KMS access.

Restrict access to metrics and avoid unbounded request metadata labels. Never expose credentials as labels. See the
[metrics configuration](/production-deployment/temporal-proxy#observability) for label controls.

## Grant access to your KMS key

The one thing the chart cannot do for you is grant the proxy access to your cloud KMS key. When you enable
[payload encryption](/production-deployment/temporal-proxy/encrypt-payloads), the proxy needs a cloud identity that
holds the encrypt and decrypt permissions on the key. Bind the chart's Kubernetes ServiceAccount to that identity with
workload identity, so the proxy authenticates to your KMS with no static credentials. If you do not use encryption, you
can skip this: API keys and TLS material come from the configuration and mounted Secrets, so the proxy needs no cloud
identity.

Grant the cloud identity the encrypt and decrypt permissions first, as described under
[Encrypt payloads](/production-deployment/temporal-proxy/encrypt-payloads), then bind it to the ServiceAccount as shown
below. The bindings reference the ServiceAccount by name, so set `serviceAccount.name` in your values to keep it stable
and matching what you bind on the cloud side.

### AWS IRSA and Pod Identity

Create an IAM role whose trust policy lets your cluster's OIDC provider assume it from the proxy's ServiceAccount, and
attach the KMS policy from [AWS KMS](/production-deployment/temporal-proxy/encrypt-payloads#aws-kms). Then annotate the
ServiceAccount with the role ARN:

```yaml
serviceAccount:
  name: temporal-proxy
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/temporal-proxy
```

On EKS you can use [Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html) instead: create
an association between the role and the ServiceAccount with `aws eks create-pod-identity-association`, and no annotation
is required.

### Azure Workload Identity

Create a federated identity credential that links a user-assigned managed identity (holding the key permissions) to the
proxy's ServiceAccount subject:

```bash
az identity federated-credential create \
  --name temporal-proxy \
  --identity-name <managed-identity-name> \
  --resource-group <resource-group> \
  --issuer <aks-oidc-issuer-url> \
  --subject system:serviceaccount:<namespace>:temporal-proxy
```

Then annotate the ServiceAccount with the identity's client ID and label the Pods so the webhook injects credentials:

```yaml
serviceAccount:
  name: temporal-proxy
  annotations:
    azure.workload.identity/client-id: <client-id>

podLabels:
  azure.workload.identity/use: 'true'
```

### GCP Workload Identity

Bind the Google service account (GSA) that holds the key permissions to the proxy's Kubernetes service account (KSA):

```bash
gcloud iam service-accounts add-iam-policy-binding \
  proxy@my-project.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:my-project.svc.id.goog[NAMESPACE/KSA_NAME]"
```

Then annotate the ServiceAccount through Helm so GKE maps it to the GSA:

```yaml
serviceAccount:
  name: temporal-proxy
  annotations:
    iam.gke.io/gcp-service-account: proxy@my-project.iam.gserviceaccount.com
```
