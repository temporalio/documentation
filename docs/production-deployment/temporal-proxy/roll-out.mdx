  releases. Pin a version and check its [configuration schema](https://github.com/temporalio/temporal-proxy) before

This guide is for teams whose Workers and SDK Clients already connect to Temporal Cloud and use a
[Payload Codec](/payload-codec) to encrypt payloads. You will move encryption of new payloads to Temporal Proxy while
preserving other codec functions and access to existing encrypted history.

We recommend a migration with two stages:

1. Move your Workers and SDK Clients onto the proxy while keeping their existing Payload Codec encryption.
2. Enable proxy encryption, then stop encrypting new payloads in the SDKs while retaining legacy decoding.

Keep the same Temporal Cloud Namespace, Task Queues, Workflow IDs, and Workflow code through both stages. Existing
Workflow Executions continue in that Namespace; this migration does not copy or restart them.

A [Codec Server](/codec-server) is a separate, optional HTTP service for UI and CLI payload encoding and decoding.
Your Workers and SDK Clients run their Payload Codecs as part of their Data Converters; they do not need to connect to
that Codec Server. Configuring the UI and CLI to use Proxy's HTTP endpoint is an independent process, covered at the
[end of this guide](#configure-ui-and-cli).

## Identify what your Payload Codec does

Inventory the Data Converter configuration in every Worker and SDK Client. Record the encryption format, the value
written to `metadata.encoding`, and all keys needed to decrypt existing data. Include Workflow and Activity Workers,
Workflow starters, message senders, Schedule management tools, and asynchronous Activity completion processes.

Proxy encrypts serialized payloads on the hop to Cloud and decrypts its encryption layer on responses. This lets you
manage new encryption and KMS policies at Proxy, but it does not replace every transformation in your Data Converter:

| Current responsibility | What changes with Proxy | What to retain |
| --- | --- | --- |
| Payload encryption | Proxy can encrypt new payloads after the SDK has serialized and transformed them. | Keep your previous codec's decryption logic and keys while existing data needs them. |
| Payload compression | Proxy's built-in codec chain does not compress or decompress payloads. | Keep compression and decompression in the SDK codec chain if you use them. |
| Custom serialization | Proxy forwards serialized payloads and restores them after decrypting its own layer. | Keep your Payload Converter and any custom serialization or metadata transformations. |
| Failure encoding | Payload encryption alone does not encrypt failure messages and stack traces. | Keep your Failure Converter behavior unless you explicitly migrate and test it. Supported Proxy versions provide `encryption.failures`. |
| External Storage | Proxy does not replace your storage driver or the logic that retrieves external payloads. | Keep storage access and the transformations applied to externally stored data. |

If one custom codec combines compression and encryption, separate the functions or add a mode that stops new
encryption while preserving compression and legacy decryption. Do not replace the entire Data Converter with its
default just to remove encryption.

With compression retained, new outbound data follows this order: serialize in the SDK, compress in the SDK, encrypt
at Proxy, then send to Cloud. Responses reverse that order: Proxy decrypts its layer, the SDK decompresses the payload,
and the Payload Converter reconstructs the application value. Compression happens before encryption because
ciphertext does not compress effectively.

Proxy does not automatically import your existing codec format or keys. Using the same encryption algorithm or KMS
key does not make the formats compatible. Plan to retain legacy SDK decryption until no required data uses that format.

## Plan your Temporal Proxy deployment model

Choose how your existing Workers and SDK Clients will reach Proxy before changing their connections:

- [Choose a deployment model](/production-deployment/temporal-proxy/deploy-kubernetes#choose-a-deployment-model) for
  sidecar and shared-service considerations.
- [Configure TLS](/production-deployment/temporal-proxy/configure#configure-tls) for securing application-to-proxy and
  proxy-to-Cloud connections, and [Route requests](/production-deployment/temporal-proxy/configure#route-requests) for
  selecting upstream endpoints.
- [Authenticate and authorize inbound requests](/production-deployment/temporal-proxy/configure#authenticate-and-authorize-inbound-requests)
  and [Present credentials to upstreams](/production-deployment/temporal-proxy/configure#present-credentials-to-upstreams)
  for configuring access to Proxy and Temporal Cloud separately.
- [Deploy to Kubernetes](/production-deployment/temporal-proxy/deploy-kubernetes) for Helm configuration, Secrets, health
  probes, shutdown, and KMS access.

Proxy will see payloads without the SDK encryption layer once you stop local encryption. Place it within your trust
boundary and protect the application-to-proxy connection. After choosing the deployment model, begin with proxy
payload encryption disabled.

## Connect through Proxy with your existing codec (phase 1)

Deploy Proxy without changing payload encoding. Preserve the full Cloud Namespace name in applications and omit
Namespace translation for this stage.

For a local proxy, save the following as `config.yaml`. Set `TEMPORAL_CLOUD_ADDRESS` to your existing Cloud endpoint,
including port `7233`, and supply `TEMPORAL_API_KEY` through your secret management system. The API key must have access
to the existing Namespace.

```yaml
hostPort: 127.0.0.1:7233

routing:
  default: cloud
  system: cloud

upstreams:
  - name: cloud
    hostPort: ${TEMPORAL_CLOUD_ADDRESS}
    credentials:
      static:
        apiKey: ${TEMPORAL_API_KEY}

encryption:
  enabled: false
```

Proxy dials Cloud over TLS by default in v0.6.0 and later. The `system` route sends Namespace-less requests, such as
the SDK's connection-time `GetSystemInfo` call, to the same fixed endpoint. If you use mTLS, configure the upstream's
certificate, key, and CA instead of the API key as described in
[Configure TLS](/production-deployment/temporal-proxy/configure#configure-tls).

Start Proxy with this configuration:

```command
proxy serve --config config.yaml
```

The `--config` flag selects the YAML file. This example serves plaintext only on loopback. For a shared deployment,
use the secured gateway address and configure applications to trust its certificate and present its required
credentials.

Move a test Worker and SDK Client first, then expand one deployment at a time:

1. Change the SDK connection address to the proxy endpoint. For the loopback example, use `127.0.0.1:7233`, disable
   Cloud-specific TLS on that local connection, and remove Cloud credentials from it. For a secured shared gateway,
   use its TLS and authentication settings instead. Proxy presents the Cloud credentials upstream.
2. Keep the full Namespace name, Task Queue names, and Data Converter configuration unchanged. The Payload Codec
   continues encrypting outbound payloads and decrypting responses.
3. Verify that a new Workflow starts, executes an Activity, and returns a result. Restart a Worker and verify that
   an existing Workflow replays from encrypted history and handles messages used by your application.
4. Move the remaining Workers and SDK Clients. Shut down Workers gracefully and verify that replacement Workers
   poll the intended Task Queues.

During this stage, direct and proxied applications can share the Namespace because payload encoding is unchanged.
An existing UI/CLI Codec Server continues to work independently with the same payload format.

Compare request errors, latency, Worker polling, and Task Queue backlog with your baseline. Proxy health alone does
not prove that Cloud authentication or application decoding works. Once all application connections use Proxy,
prepare the decoders before moving encryption out of the SDKs.

## Prepare your SDK decoders for both payload formats

Update each encryption codec so its decoder accepts both legacy encrypted payloads and payloads without the legacy
encryption layer. Keep its encoder encrypting new data during this preparation. Depending on your implementation,
this may require changing the custom codec rather than setting a built-in SDK option.

The decoder must recognize its own encryption metadata, decrypt legacy data with the original keys, and pass other
payloads through to the remaining codec chain. Preserve decompression and custom transformations in the correct
order. Test both formats across every SDK and Worker deployment you use before changing any encoder.

After migration, an existing history event still contains your old ciphertext: Proxy passes it through and the SDK
codec decrypts it. For a new event encrypted by Proxy, Proxy removes its layer before returning the payload, and the
SDK only applies the remaining transformations, such as decompression. SDK applications behind Proxy do not need to
implement Proxy's ciphertext format.

Check every application that consumes payloads, including result readers and asynchronous Activity processes. A
Worker or SDK Client that bypasses Proxy needs a decoder for Proxy's format to read those new payloads. Move these
connections before enabling proxy encryption; moving only Workflow starters is insufficient.

## Enable Proxy encryption and stop SDK encryption (phase 2)

Provision a KMS key and grant the proxy identity encrypt and decrypt permissions. Configure every proxy serving the
Namespace with compatible key policies, initially in decrypt-only mode. Add this fragment to the existing
configuration, replacing the example AWS key ARN and encoding name with your own:

```yaml
encryption:
  enabled: false
  skipEncodings:
    - binary/your-existing-encryption
  default:
    uri: awskms:///arn:aws:kms:us-east-1:123456789012:key/abcd-1234?region=us-east-1
    duration: 1h
    renewBefore: 15m
```

See [Encrypt payloads](/production-deployment/temporal-proxy/encrypt-payloads) for other KMS providers and key policies.
Restart each proxy to load the configuration. With keys configured, decryption runs even when `enabled: false`.
Test that each replica can decode data written by an encryption-enabled proxy in a test Namespace, including across
regions if your proxies span regions.

`skipEncodings` lets the existing SDK ciphertext pass through without adding a second encryption layer during the
migration. Use the actual encoding value on the encrypted payload your SDK sends. Proxy trusts this marker; it does
not verify that skipped payloads are encrypted. Do not list the unencrypted or compressed-only encoding that you will
send after disabling SDK encryption. If you list `binary/encrypted`, Proxy also passes through responses encrypted
under unknown keys, so monitor `unknown_key` results. Check your version's
[skip behavior](https://github.com/temporalio/temporal-proxy/blob/main/pkg/codec/encryptor.go).

Complete the switch in this order:

1. Enable `encryption.enabled: true` in a test Namespace and validate both old SDK ciphertext and new Proxy ciphertext.
2. Set `encryption.enabled: true` on every production proxy replica and restart them in batches. Keep SDK encryption
   enabled until all replicas are ready. During this rollout, the existing SDK ciphertext remains protected and is
   forwarded according to `skipEncodings`.
3. Stop **new encryption** in the SDK Payload Codec, one application deployment at a time. Keep legacy decryption,
   decompression, serialization, and any other required transformations. A Worker still using the old encoder and one
   using the new encoder can coexist once both decoders accept both formats and all their connections use Proxy.
4. Verify that newly written payloads without the old encryption marker receive Proxy encryption before reaching
   Cloud. Keep the original codec's keys available for old history.

Do not stop SDK encryption while any of those applications can reach an encryption-disabled proxy or connect directly
to Cloud. That would allow new payloads to bypass the replacement encryption path. Proxy fails requests when it cannot
encrypt required payloads; it does not fall back to plaintext.

Without `skipEncodings`, Proxy adds an outer layer around SDK ciphertext until you disable the old encoder. That
requires testing the two-layer decode path, including in UI/CLI tools. Use it only if you intend to retain both layers.
Once new encryption is handled by Proxy, validate the complete application migration.

## Validate the migration

Use representative Workflows and payload sizes to verify the new behavior before retiring any old codec logic:

- Restart a Worker and replay an existing Workflow with legacy encrypted history, then process new work encrypted by
  Proxy in the same execution.
- Exercise Workflow and Activity inputs and results, Signals, Updates, Queries, and heartbeats used by your application.
- Verify that retained compression and custom serialization still work. Include large payloads: Proxy adds encryption
  overhead and does not compensate for removing compression.
- Inspect new raw history directly from Cloud without decoding to confirm that Proxy encryption metadata is present.
- Replace a proxy replica and test KMS failure in a test environment to verify retries and error handling.

Watch [Proxy metrics](/production-deployment/temporal-proxy#observability), application errors, and Task Queue backlog.
Investigate failed KMS operations, unexpected skipped payloads, or unknown-key results before advancing a batch.

Proxy encryption changes new writes; it does not rewrite old Event History or encrypt Search Attributes and
identifiers. Failure messages and stack traces need separate failure encoding. Preserve your existing
[Failure Converter](/failure-converter), or explicitly configure and test `encryption.failures: true` on a version
that supports it. See [Encryption coverage](/production-deployment/data-encryption) for the boundaries.

Keep legacy decryption and keys for as long as required data uses them. Include open Workflow Executions, Schedule
payloads, retained closed histories, exports, and archived data you still need to read. Waiting one retention period
after the connection change is insufficient for long-running Workflows. After validation, restrict unused direct
application connections to Cloud. Configure UI and CLI access independently using the final section.

## Roll back without losing access to history {/* #roll-back */}

Before Proxy has written encrypted data, you can restore the previous direct Cloud connections and credentials with
your original Payload Codec configuration.

After Proxy has written encrypted data, keep the application connections through a compatible proxy. You can stop
new proxy encryption with `encryption.enabled: false`, but retain its key policies and KMS decrypt permissions so
existing Proxy ciphertext remains readable. If `encryption.failures` is enabled, disable it too.

Restore SDK encryption on every producer before disabling Proxy encryption when new payloads must remain encrypted.
Keep the decoder that accepts both legacy encrypted data and the payloads returned by Proxy. Restoring an old
application release that rejects payloads without its original encryption layer is not a compatible rollback.

Do not reconnect directly to Cloud unless the application's decoder understands every stored format. Preserve the
compression and other transformations needed by both old and new data. Disabling Proxy encryption does not decrypt
stored history. Retain old Proxy keys through `decryptURIs` when changing key policies, as described in
[Encrypt payloads](/production-deployment/temporal-proxy/encrypt-payloads).

## Configure UI and CLI to use Temporal Proxy instead of a Codec Server {/* #configure-ui-and-cli */}

This is separate from the Worker and SDK Client migration. The Cloud UI and CLI can use Proxy's built-in HTTP Codec
Server endpoint for payloads encrypted only by Proxy. Workers and SDK Clients use the gRPC gateway; they do not use
this HTTP endpoint to execute Workflows or Activities.

Enable the HTTP listener with the same Proxy key policies used by your applications. The following fragment uses the
current `http.codecServer` schema. Supply the TLS files, add it to the proxy configuration, and restart Proxy:

```yaml
http:
  hostPort: :8443
  tls:
    cert: /etc/temporal-proxy/certs/codec/tls.crt
    key: /etc/temporal-proxy/certs/codec/tls.key
  codecServer:
    enabled: true
    cors:
      origins:
        - https://cloud.temporal.io
      credentials: true
    auth:
      jwks:
        url: https://login.tmprl.cloud/.well-known/jwks.json
```

This fragment authenticates Cloud UI tokens. Switch the tools' codec endpoint:

1. In the Cloud UI's Codec Server settings for your Namespace, set the endpoint to Proxy's HTTPS base URL and enable
   **Pass access token**. Your browser must be able to reach the listener and trust its TLS certificate. The hosted
   Cloud UI still connects directly to Cloud for Temporal requests; only its HTTP codec calls change destination.
2. For CLI commands connecting directly to Cloud, keep the Cloud address and credentials and set `--codec-endpoint`
   to Proxy's HTTPS base URL. Supply credentials accepted by its HTTP authentication configuration.
3. Verify that both tools display Proxy-encrypted payloads and can encode inputs accepted by your Workers. If you need
   this access during the application migration, configure it before Proxy begins writing the new format.

Authentication does not by itself restrict decryption per Namespace. Configure the authorization required for your
users and keys; see the [Proxy Codec Server reference](https://github.com/temporalio/temporal-proxy#codec-server).
The CLI can alternatively connect through Proxy's gRPC gateway, which removes the proxy encryption layer on responses.

An endpoint change is sufficient only if Proxy handles every transformation those tools need. Its built-in Codec
Server does not run your legacy Payload Codec or decompress payloads compressed by your SDKs. Keep your existing Codec
Server, or provide a combined handler that removes Proxy encryption and then applies legacy decryption, decompression,
and other required transformations in the correct order. Preserve retrieval logic for
[External Storage](/codec-server#external-storage) too. Test both old and new history before retiring the original
server; moving SDK encryption to Proxy does not remove these UI/CLI requirements.
