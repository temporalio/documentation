Platform engineers running Temporal Proxy between their Workers, Clients, and Temporal Cloud must provision capacity
for peak traffic and for reconnects after a disruption. This guide covers replica sizing, placement, scaling, rollouts,
and monitoring. First [deploy the proxy](/production-deployment/temporal-proxy/deploy-kubernetes) and configure its
upstreams and, if needed, [payload encryption](/production-deployment/temporal-proxy/encrypt-payloads).

**Load-test your workload before using the capacity figures.** The
[reference results](/production-deployment/temporal-proxy/performance) come from one 4-CPU replica on an unspecified
pre-release build. They are measurements under specific conditions, not throughput guarantees. Fleet sizing and other
CPU sizes are extrapolations. All YAML below is an example to adapt and validate.

## Size each replica

Measure CPU cost as cores per 1,000 requests per second, using the queries under [Monitor each pod](#monitor-each-pod).
Payload size, request mix, encryption, and garbage collection all affect this figure. Long polls and Activity result
polls dominated the reference request rate; a mix with more payload-carrying calls can have a lower ceiling.

### Allocate CPU

The reference tests were CPU-bound. Small unencrypted payloads used about 0.29 to 0.31 cores per 1,000 requests per
second. Encrypted payloads used about 0.33 to 0.36; payloads averaging 900 KB used about 0.8. Past CPU saturation,
throughput fell rather than staying at its maximum.

Plan to run each replica at 65% to 75% of its measured ceiling. Choose smaller replicas for smaller capacity increments
and less impact from a pod failure. Larger replicas need fewer pods and connections, but test their throughput rather
than assuming it grows linearly with CPU.

Choose CPU requests and limits together:

| Choice | Benefit | Planning constraint |
| --- | --- | --- |
| Equal CPU and memory requests and limits, giving Guaranteed quality of service (QoS) | Predictable reserved capacity and lower eviction priority under node pressure | The CPU limit prevents bursts above the allocation. This matches the reference tests. |
| CPU request below its limit, or no CPU limit, giving Burstable QoS | Higher pod density and room to use spare node CPU | Plan from the request. Available capacity depends on other workloads on the node. |

Go 1.25 and later accounts for the cgroup CPU limit when choosing `GOMAXPROCS`. Without a CPU limit, the default can
reflect the node's CPUs. Consider setting `GOMAXPROCS` explicitly, such as to the CPU request rounded up, and validate
that choice under load. See [Go's container support](https://go.dev/doc/go1.25#container-aware-gomaxprocs).

Watch `container_cpu_cfs_throttled_periods_total` for CPU throttling. Sustained throttling indicates that you need more
capacity. Guaranteed pods with integer CPU requests can optionally use the kubelet's
[`static` CPU manager policy](https://kubernetes.io/docs/tasks/administer-cluster/cpu-management-policies/) for exclusive
CPUs.

### Allocate memory

Set `GOMEMLIMIT` to about 85% to 90% of the container memory limit as an initial target. The Go runtime does not derive
this setting from the container memory limit. Without it, heap growth during a reconnect burst can cause Kubernetes to
kill the pod for running out of memory.

The following are **provisional starting points**, not validated minimums. The throughput tests used a 12Gi memory
limit and `GOMEMLIMIT=11GiB`; limits below 12Gi were not validated with 100 or more Workers per replica.

| Workload | Memory request and limit | `GOMEMLIMIT` |
| --- | --- | --- |
| Small payloads, fewer than about 30 Workers per replica | `3Gi` | `2700MiB` |
| Small payloads, 100 or more Workers per replica | `6Gi` | `5400MiB` |
| Payloads near 1 MB | `12Gi` | `11GiB` |

`GOMEMLIMIT` is a soft limit, not a cap on resident set size (RSS). A smaller limit increases garbage collection (GC)
work and can reduce throughput. If the live working set exceeds the limit, the process can still run out of memory.
Re-measure CPU cost and RSS at the memory limit you select.

Avoid memory-based autoscaling: RSS can remain high after traffic falls. The chart source on `main` disables the memory
target by default. Published chart 0.2.1 enables it; set `autoscaling.targetMemoryUtilizationPercentage: null`.

### Allocate upstream connections

Keep `connection.maxConnections` near 32 as a starting point. The current proxy default is 32 per target, with a maximum
of 64. Older releases defaulted to one connection, so check your version or set the value explicitly.

Each long poll occupies an HTTP/2 stream. In the reference tests, pools of one to four connections exhausted available
streams and caused calls to stall or time out. A pool of 32 worked at about 13,000 requests per second with 200 Workers.

Set this under `config` in your Helm values:

```yaml
config:
  upstreams:
    - name: cloud
      hostPort: your-namespace.your-account.tmprl.cloud:7233
      connection:
        maxConnections: 32
```

This fragment only sets the connection pool. Add the routing, TLS, and credentials from your
[proxy configuration](/production-deployment/temporal-proxy/configure).

A templated upstream has a pool for each resolved target, often one per Namespace. SRV discovery applies the pool size
per backend. Estimate total upstream connections as pool size multiplied by targets and replicas, and account separately
for Cloud Ops API connections. Reduce the pool size if serving many targets would exceed your connection budget.

## Place replicas on nodes

Use node **allocatable** CPU and memory, which exclude system and kubelet reservations, when calculating pod density.
Subtract DaemonSet requests, then calculate CPU capacity:

```text
proxies_per_node = floor((allocatable_cpu - daemonset_cpu_requests) / proxy_cpu_request)
```

Repeat this calculation for memory and use the smaller result. A pod requesting four CPUs generally cannot fit on a
four-vCPU node because allocatable CPU is below node capacity.

For example, with 0.5 CPU reserved for DaemonSets and a 4-CPU proxy request, the following AWS Graviton c6g node sizes
give these CPU-only estimates:

| Node capacity | Allocatable CPU | Proxies per node | Unused CPU as a share of node capacity |
| --- | --- | --- | --- |
| 8 vCPU, 16 GiB | About 7.9, measured | 1 | About 43% |
| 16 vCPU, 32 GiB | About 15.9, estimated | 3 | About 22% |
| 32 vCPU, 64 GiB | About 31.8, estimated | 7 | About 10% |

Check memory before choosing a node: a 32 GiB node cannot hold three replicas that each request 12Gi. A 3.5-CPU request
with a 4-CPU limit can fit two replicas on the 8-vCPU example node, but makes them Burstable; plan from 3.5 CPUs.

Spread replicas across zones with `topologySpreadConstraints`, using `topology.kubernetes.io/zone`, `maxSkew: 1`, and
`whenUnsatisfiable: DoNotSchedule`. Use a replica count divisible by the number of zones. `ScheduleAnyway` permits
uneven placement. The chart does not expose `topologySpreadConstraints`; add it with a Helm post-renderer or manage the
Deployment directly.

A dedicated node pool can reduce interference and node consolidation, at the cost of idle capacity. On platforms such
as EKS Fargate or GKE Autopilot, focus on pod requests and the platform's placement and disruption controls.

## Plan the replica count

Start from peak requests per second and a per-replica ceiling measured on your workload. Reserve one extra replica
for a pod failure or rollout:

```text
planned_requests_per_replica = measured_ceiling * target_utilization
replicas = ceil(peak_requests_per_second / planned_requests_per_replica) + 1
```

Use a target utilization of 0.65 to 0.75. To tolerate losing one of `Z` equally populated zones, also require:

```text
peak_requests_per_second / (replicas * (Z - 1) / Z) <= 0.75 * measured_ceiling
```

Choose a multiple of the zone count that meets **both** the normal peak sizing and the zone-loss requirement.
The [worked examples](/production-deployment/temporal-proxy/performance#calculate-fleet-capacity) illustrate this
calculation; they were not validated with a fleet test.

Check per-pod load as well as total capacity. Long-lived Client connections do not redistribute automatically when a
replica is added. A rollout in the reference tests left two pods carrying 99.6% and 0.4% of requests. A few high-traffic
Clients can overwhelm one pod even when total fleet capacity is sufficient.

Keep your [Temporal Cloud Namespace limits](/evaluate/cloud/limits) in the plan. Adding proxy replicas does not increase the
Namespace's request or Action limits.

## Use autoscaling as a safety net

Set the minimum replica count to your static peak sizing. A CPU-based HorizontalPodAutoscaler (HPA) can add capacity for
new connections, but it cannot move existing connections away from a saturated pod. The idle replica can also lower
average CPU utilization enough to stop further scaling.

Use CPU utilization against the **request**, which requires a CPU request but not a CPU limit. Start with a 65% target,
scale up quickly, and scale down slowly, one pod at a time. Alert on per-pod saturation and uneven load even when the
average looks healthy. Per-pod maximum CPU or request-rate scaling requires a metrics adapter or a tool such as KEDA;
it still cannot redistribute established connections.

This Helm values example uses six replicas as the peak minimum and the scaling behavior in the chart source on `main`:

```yaml
autoscaling:
  enabled: true
  minReplicas: 6
  maxReplicas: 12
  targetCPUUtilizationPercentage: 65
  targetMemoryUtilizationPercentage: null
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 900
      policies:
        - type: Pods
          value: 1
          periodSeconds: 300
```

Choose `minReplicas` and `maxReplicas` from your capacity and upstream limits. The chart defaults to
`minReplicas: 1`, so it does not provide redundancy without an override. With `autoscaling.enabled: true`, the chart
omits the Deployment's `replicas` field so a Helm upgrade does not reset the HPA's count.

Published chart 0.2.1 does not support `behavior`; use a post-renderer to add it or accept Kubernetes defaults. If you create an
HPA through `extraObjects` while `autoscaling.enabled` is false, remove the Deployment's `replicas` field with a
post-renderer to prevent Helm upgrades from resetting it.

If a hot pod needs traffic redistributed, test how your Client's connection behavior responds to reconnects. Stagger
any Client restarts and monitor throughput; restarting all Clients together caused recovery periods of several minutes
in the reference tests. Avoid scale-ups and restarts during KMS or extension outages because new pods may not start.

## Control rollouts and disruptions

Use the [probe and shutdown settings](/production-deployment/temporal-proxy/deploy-kubernetes#probe-the-gateway) with a
rollout strategy that preserves spare capacity. A TCP readiness probe detects whether the listener is open; it does not
validate TLS, upstream reachability after startup, or KMS access. Keep liveness independent of these dependencies to
avoid turning a dependency outage into repeated restarts.

| Strategy | Capacity requirement | Trade-off |
| --- | --- | --- |
| `maxSurge: 1`, `maxUnavailable: 0` | A free node slot large enough for a full replica | Kubernetes waits for a replacement to become available before removing an old pod. A TCP probe can still miss a faulty replacement. |
| `maxSurge: 0`, `maxUnavailable: 1` | Peak capacity plus one replica | Uses the spare replica without adding a node. An unhealthy replacement consumes that margin. |

The chart source on `main` defaults to the first strategy, `minReadySeconds: 15`, a 15-second native `preStop` sleep,
and a 60-second termination grace period. Published chart 0.2.1 does not expose these four fields; add them with a
post-renderer or manage the Deployment directly. The following values example for the chart source on `main` increases
the ready interval to 30 seconds and uses the provisional 6Gi memory configuration:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
minReadySeconds: 30
terminationGracePeriodSeconds: 60
lifecycle:
  preStop:
    sleep:
      seconds: 15
readinessProbe:
  tcpSocket:
    port: http
  periodSeconds: 5
  failureThreshold: 2
livenessProbe:
  tcpSocket:
    port: http
  periodSeconds: 10
  failureThreshold: 6
env:
  - name: GOMEMLIMIT
    value: '5400MiB'
resources:
  requests:
    cpu: '4'
    memory: 6Gi
  limits:
    cpu: '4'
    memory: 6Gi
podDisruptionBudget:
  maxUnavailable: 1
```

Use the native `sleep` lifecycle handler on Kubernetes versions that support it. The scratch-based proxy image has no
shell or `sleep` executable. The sleep handler was enabled by default starting in Kubernetes 1.30. Confirm support on
your cluster before applying this configuration. See
[Container lifecycle hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/).

The grace period must cover the `preStop` delay and the proxy's 30-second shutdown budget. A PodDisruptionBudget limits
voluntary evictions, such as node drains; it does not control Deployment rollouts or prevent node failures.

For slow startup, add a `startupProbe` with a post-renderer; the chart does not expose this field. This Deployment
fragment also illustrates zone spreading. Match the selector to your release's labels:

```yaml
spec:
  template:
    spec:
      containers:
        - name: temporal-proxy
          startupProbe:
            tcpSocket:
              port: http
            periodSeconds: 5
            failureThreshold: 24
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: temporal-proxy
              app.kubernetes.io/instance: your-release
```

Limit voluntary node disruption to maintenance windows. Each pod move in the reference tests caused two to five minutes
of recovery and could increase load skew. Depending on your node autoscaler, use a Karpenter NodePool with
`consolidationPolicy: WhenEmpty`, the pod annotation `karpenter.sh/do-not-disrupt: 'true'`, or the Cluster Autoscaler
annotation `cluster-autoscaler.kubernetes.io/safe-to-evict: 'false'`. These controls do not prevent spot reclamation or
node failure.

## Handle dependency failures

Check the failure cause before adding replicas:

| Symptom or dependency | Behavior | Action |
| --- | --- | --- |
| Upstream `ResourceExhausted` with low proxy CPU | The Namespace may be rate-limited. | Check Namespace limits and request rates. Contact Temporal if you need more capacity. |
| Static upstream unreachable at startup | Startup fails before the gateway opens. Templated upstreams connect on first use. | Pause rollouts during an upstream connectivity incident. |
| Failure to open a configured KMS key or connect to an extension server at startup | Startup fails, including when opening keys configured only for decryption. A cloud KMS provider determines which checks happen when the key is opened. Kubernetes restart backoff can delay recovery. | Avoid rollouts, evictions, and restarts during an outage. Remove unused keys and extensions only after verifying they are no longer needed. |
| KMS unreachable while pods are running | New DEK wraps and unwraps fail. Cached keys can serve some requests, but do not guarantee continued service. | Monitor KMS failures and keep spare running capacity. Size the DEK cache for the active key working set. |
| Request exceeds the proxy's 4 MiB receive limit | The call fails with `ResourceExhausted` and a message such as `received message larger than max`. | Reduce request size; adding replicas does not help. |
| Key removed while encrypted data still exists | The proxy cannot decrypt payloads sealed with that key. | Retain decryption access for Event History, Visibility, and archived data for as long as the data exists. |

With encryption enabled, each replica creates its own data encryption key (DEK) per Namespace and rotates it on a
schedule. Reading another replica's payload or an older payload can require a KMS unwrap if the decrypted DEK is not
cached. The default cache holds 100 entries. Estimate the working set from replicas, Namespaces, and the DEKs still
being read, then measure the cache miss ratio. Do not disable the cache for routine operation: the reference test with
`cacheSize: 0` generated about 2,800 KMS calls per second and used 22% more CPU per request than unencrypted traffic.

Use `renewBefore` to pre-rotate DEKs before expiry, allowing time for temporary KMS failures. It does not protect
cache misses or a cold pod from a KMS outage. See
[key policy settings](/production-deployment/temporal-proxy/encrypt-payloads) for configuration and key retirement.

For oversized Workflow Task completions, return fewer large Local Activity results in one task or store payloads
externally and pass a reference. Check [Temporal Cloud limits](/evaluate/cloud/limits) for Payload and Event History limits as
well as request limits.

## Monitor each pod

Scrape `/metrics` at `metrics.hostPort`, which defaults to `:9090`. The metric prefix defaults to `tmprl_proxy`. The
chart does not declare a metrics container port or create a PodMonitor, so configure your scraper to reach this port.
See the [metric definitions](/production-deployment/temporal-proxy#observability).

Scope all queries to the same proxy deployment. The examples assume the scraper attaches `job="temporal-proxy"` and
a `pod` label; change these selectors to match your labels.

Measure requests per second for each pod:

```promql
sum by (pod) (rate(tmprl_proxy_server_requests_total{job="temporal-proxy"}[2m]))
```

Compare maximum per-pod load with average per-pod load to detect skew:

```promql
max(sum by (pod) (rate(tmprl_proxy_server_requests_total{job="temporal-proxy"}[5m])))
  / avg(sum by (pod) (rate(tmprl_proxy_server_requests_total{job="temporal-proxy"}[5m])))
```

A pod with no request-counter series is absent from this calculation. Compare it with the expected replica count so an
unused or stalled pod does not go unnoticed.

Calculate cores per 1,000 requests per second for capacity planning:

```promql
sum(rate(process_cpu_seconds_total{job="temporal-proxy"}[5m]))
  / (sum(rate(tmprl_proxy_server_requests_total{job="temporal-proxy"}[5m])) / 1000)
```

Track selected request errors separately from canceled or expired long polls:

```promql
sum(rate(tmprl_proxy_server_requests_total{job="temporal-proxy",code=~"Unavailable|Internal|Unknown|ResourceExhausted"}[5m]))
  / sum(rate(tmprl_proxy_server_requests_total{job="temporal-proxy"}[5m]))
```

`Canceled` and `DeadlineExceeded` can occur during ordinary long polling. Investigate unexpected changes in those codes
separately. Exclude `Poll*` methods when analyzing short-request latency; long polls can wait about 60 seconds.

Inspect Workflow Task completion rejections, then check logs to distinguish request-size failures from upstream limits:

```promql
sum by (pod) (rate(tmprl_proxy_server_requests_total{job="temporal-proxy",code="ResourceExhausted",method=~".*RespondWorkflowTaskCompleted"}[5m]))
```

Use these alert thresholds as starting points to validate against your normal workload:

| Alert | Initial condition | Investigate |
| --- | --- | --- |
| Saturation | Per-pod CPU exceeds 85% of its planned CPU allocation for 10 minutes | CPU throttling, capacity, and Client distribution |
| Skew | Maximum-to-average request rate exceeds 1.5 for 15 minutes | Connection distribution; stagger reconnects if needed |
| Request errors | The selected error ratio exceeds 1% for 5 minutes | gRPC codes, upstream errors, and proxy logs |
| `ResourceExhausted` | Errors continue for 5 minutes | Message-size rejections versus Namespace rate limits |
| Memory pressure | RSS exceeds 90% of `GOMEMLIMIT` for 10 minutes | GC activity and memory headroom; RSS is not the Go runtime's memory-limit accounting |
| Restart | Any unexpected restart or `CrashLoopBackOff` | KMS, extension, and upstream reachability, followed by container termination reason |
| KMS or cache pressure | `tmprl_proxy_encryption_kek_ops_total{result="error"}` increases, or cache miss ratio stays above 1% | KMS availability and decrypted-DEK cache capacity |
| Stalled pod | A previously busy pod approaches zero requests per second and uses less than 0.1 CPU while peers remain busy | Process health; a TCP probe can miss this state |

Watch `tmprl_proxy_router_forwarding_errors_total` for proxy-originated failures, and the encryption KMS duration,
cache-hit, cache-miss, and DEK-rotation metrics for encryption health. Rising `on_demand` rotations can indicate that
pre-rotation is falling behind. Go runtime and process metrics expose GC, goroutine counts, CPU, and RSS.

Restrict metrics access and avoid labels per Worker or freely chosen request metadata. Each distinct label value creates
additional series. The `method` label can reflect a caller-supplied path, so expose the proxy only to trusted callers.

## Validate your deployment

Run a load test using your production request mix, payload sizes, encryption settings, and CPU and memory limits.
Ramp concurrency until throughput stops increasing, recording CPU cost, RSS, error ratio, and network bytes per second.

Then test the full fleet: delete a pod, simulate zone loss, perform a rolling upgrade, and reconnect Clients. Record
recovery time and per-pod skew. Test KMS and extension failures in an isolated environment. Use these results to revise
replica counts, resource settings, and alerts before relying on the deployment's capacity.
