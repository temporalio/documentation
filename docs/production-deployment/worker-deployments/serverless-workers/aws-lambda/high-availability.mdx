Deploy a Lambda function in each of your Temporal Cloud Namespace's regions, then configure both functions on the same
Worker Deployment Version. After Namespace failover, Temporal can invoke the function configured for the replica
region.

For details about compute selection and Worker behavior during failover, see
[Serverless Workers and High Availability](/serverless-workers#high-availability).

## Prerequisites {/* #prerequisites */}

- A Temporal Cloud Namespace with [Multi-region Replication](/cloud/high-availability/enable) between two AWS regions.
- A Serverless Worker deployed by following [Deploy a Serverless Worker on AWS Lambda](/production-deployment/worker-deployments/serverless-workers/aws-lambda).
- Credentials, databases, external storage, and any Codec Server or network proxy available to Workers in both
  regions. Check that both functions can reach the Namespace after failover.

## Deploy the replica function {/* #deploy-replica-function */}

1. Deploy the same Worker build to a Lambda function in the replica region. Use the same Worker Deployment name,
   Build ID, and Task Queues as the primary function.
2. [Publish a Lambda function version](/production-deployment/worker-deployments/serverless-workers/aws-lambda#publish-lambda-version)
   and record its qualified ARN. Each function must point to an immutable copy of the same Worker build; its Lambda
   version number can differ between regions.
3. [Grant Temporal invocation access](/production-deployment/worker-deployments/serverless-workers/aws-lambda#configure-iam)
   to the replica function. Check that the invocation role's permissions include the replica function and its
   published versions.

Repeat for every Worker Deployment Version that must serve work after failover, including older versions serving
pinned Workflows. Keep their replica functions available while those versions serve work.

## Configure regional compute {/* #configure-regional-compute */}

1. In the Temporal Cloud UI, open your Namespace and select **Workers** > **Deployments**.
2. Select your Worker Deployment, then edit the compute configuration for the version.
3. Enable **Serverless** for both Namespace regions.
4. For each region, enter the qualified ARN of the function deployed there as **Lambda ARN**. Set **IAM Role ARN**
   to the invocation role ARN and **External ID** to the value configured in its trust policy.
5. Review **Access** and **Scaling and Lifecycle** settings for both regions. Replace any suggested function ARN that
   does not match the function you deployed, then click **Save**.
6. Confirm that the version shows compute coverage for both regions.

Use functions in separate AWS regions. Assigning two compute configurations to different Namespace regions does not
protect against a regional outage if both function ARNs point to the same AWS region.

## Verify failover and failback {/* #verify-failover-and-failback */}

Use a staging Namespace to verify the configuration:

1. Run a Workflow and confirm in AWS CloudWatch Logs that the primary function processes its Tasks.
2. [Manually fail over the Namespace](/cloud/high-availability/failovers/manage#trigger-failover).
3. Let existing invocations of the primary function finish. Submit more work and confirm from the function ARN and
   AWS CloudWatch Logs that Temporal invokes the replica function and Workflows make progress.
4. Verify that the application can run without the primary region's compute or dependencies.
5. Fail the Namespace back, let remaining replica-region invocations finish, and submit more work. Confirm that
   Temporal invokes the primary function again.

Healthy invocations in the primary region can keep taking Tasks until they exit. Workflow completion alone does not
prove that the replica function served the work. Include Workflows pinned to older versions in the test.

## Recover from a Lambda outage {/* #recover-from-lambda-outage */}

Check [Lambda invocation errors](/troubleshooting/serverless-workers/aws-lambda) and Task Queue backlog. If Lambda is
unavailable in the active region, verify the replica function and its dependencies, then
[manually fail over the Namespace](/cloud/high-availability/failovers#manual-failover) to select that region's function.

A Lambda-only outage does not automatically trigger Temporal Cloud failover. Namespace failover affects all workloads
in the Namespace, so include your other Workers and Clients in the recovery procedure.
