Configure [Serverless Workers](/serverless-workers) in two regions so Temporal can launch Workers in the recovery region
after your [Temporal Cloud Namespace fails over](/cloud/high-availability). Each Worker Deployment Version holds the
compute configuration for both regions.

This guide covers Active/Passive deployments on AWS Lambda and GCP Cloud Run, with both Namespace replicas in the same
cloud provider.

## How failover affects Serverless Workers

Temporal Cloud High Availability replicates your Namespace and manages Namespace failover. Serverless Worker
configuration determines which compute Temporal starts after that failover.

The [Worker Controller Instance (WCI)](/serverless-workers#worker-controller-instance) runs where the Namespace is
active. It selects compute scaling groups configured for that Temporal region. After Namespace failover, the WCI
selects the groups for the newly active region.

A scaling group's `region_ids` identifies the Temporal regions where the configuration applies. The compute resource's
location is a separate setting: the region in a Lambda ARN or the location of a Cloud Run Worker Pool. Assigning a
scaling group to a recovery region does not deploy or move compute there.

For example, configure one Lambda function for `aws-us-east-1` and another for `aws-us-west-2` in the same Worker
Deployment Version. When the Namespace moves from east to west, Temporal starts new Workers using the west
configuration.

## Prepare compute in both regions

Before configuring failover:

- [Enable Multi-region Replication](/cloud/high-availability/enable) on your Namespace.
- Deploy the same Worker build in both compute regions, using the same Worker Deployment name, Build ID, and Task Queue
  configuration. Use immutable compute artifacts for each Build ID.
- Configure permissions for Temporal to invoke or scale both compute resources.
- Give Workers in both regions access to the Namespace, credentials, and application dependencies they need. Include
  databases, external storage, and any Codec Server or network proxy.

Follow the deployment guide for your provider to prepare the compute and access configuration:

- [AWS Lambda](/production-deployment/worker-deployments/serverless-workers/aws-lambda)
- [GCP Cloud Run](/production-deployment/worker-deployments/serverless-workers/cloud-run)

Deploy the recovery compute in a separate region. Two configurations that point to resources in the same region retain
a dependency on that region, even if they apply to different Namespace regions.

## Configure regional compute

In the Temporal Cloud UI:

1. Open your Namespace and go to **Workers**.
2. Create a Worker Deployment Version, or open an existing version and edit its compute configuration.
3. Enable **Serverless** for both Namespace regions in the compute configuration form.
4. Enter the compute target for each region:
   - For Lambda, use the qualified ARN of the function version deployed in that region and its invocation role settings.
   - For Cloud Run, use the project, Worker Pool region and name, service account, and scaling settings for that pool.
5. Review both regions' access and scaling settings. Check any suggested resource names against resources you have
   actually deployed, then save.
6. Confirm that the version shows compute coverage for both Namespace regions.

Repeat this configuration for every Worker Deployment Version that must continue processing after failover, including
versions serving pinned Workflows. Configuring one version does not configure other versions in the Deployment.

### Understand default and missing configurations

A group without `region_ids` is a default for regions without a matching regional group. Existing single-region compute
configurations keep this behavior: Namespace failover alone does not move their compute target.

If the active region has neither a matching group nor a default, the WCI does not start compute for that region. Tasks
wait for Workers that can serve that version.

You can use this intentionally to run traditional Workers in the primary region and Serverless Workers only in the
recovery region. Configure a group scoped to the recovery region, and ensure the traditional Workers use the same
Worker Deployment Version.

## Understand Workers that are already running

Failover changes where Temporal launches new Workers. It does not immediately stop Workers already running in the
original region or prevent them from receiving more Tasks.

Healthy Workers can continue reaching the active Namespace through the Namespace Endpoint or
[request forwarding](/cloud/high-availability#request-forwarding). Lambda Workers exit when their invocations end.
The controller scales Cloud Run Worker Pools that no longer serve the active region to zero on a subsequent metrics
poll.

Ensure those Workers can still reach the dependencies needed by their Activities. A Worker can reach Temporal Cloud
while its regional database or another dependency is unavailable.

If you need to restrict new Task delivery to Workers connected to the active replica, use Regional Endpoints and
[disable passive poller forwarding](/cloud/high-availability/enable#change-forwarding-behavior). Workers connected
through the Namespace Endpoint can follow the active replica regardless of their compute location. Disabling forwarding
does not terminate Activities already running.

## Test failover and recovery

Test in a staging Namespace before relying on the recovery configuration:

1. Run a Workflow and confirm from provider logs that the expected compute processes its Tasks.
2. [Trigger a manual Namespace failover](/cloud/high-availability/failovers/manage#trigger-failover).
3. Stop the original Workers safely in staging, or let existing Lambda invocations finish, then submit more work.
   Healthy original Workers can otherwise satisfy demand without Temporal starting recovery compute. Confirm that
   recovery compute starts and Workflows make progress. Check the Lambda ARN or Worker Pool location in provider logs;
   Workflow completion alone does not prove that recovery-region compute served the work.
4. Verify the application can run without compute or dependencies in the original region. Account for Workers that
   were already running there.
5. Fail the Namespace back. Repeat the test with demand that requires new Workers, and confirm they start from the
   original region's configuration.

Include Workflows pinned to older Worker Deployment Versions in your test. Recovery compute must remain available for
as long as those versions serve work.

## Respond to a compute-only outage

Monitor provider invocation or scaling errors and Task Queue backlog. Temporal Cloud's automatic failover monitors
Temporal Cloud health; an outage limited to Lambda, Cloud Run, or your application does not automatically trigger a
Namespace failover.

If compute is unavailable but Temporal Cloud is healthy, verify the recovery compute and its dependencies, then
[manually fail over the Namespace](/cloud/high-availability/failovers#manual-failover) to select the recovery
configuration. Serverless Workers cannot fail over independently of the Namespace.

Namespace failover affects all workloads in that Namespace. Include traditional Workers and Clients in your recovery
plan. See [Worker architecture patterns](/cloud/high-availability/architecture-patterns) for the rest of the application.
