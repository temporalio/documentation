Temporal's integration with [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) is an
[SDK Plugin](/develop/plugins-guide) that runs an Agent Framework `Agent` inside a Temporal Workflow. You write the
agent the way Agent Framework documents it and swap the chat client for `TemporalChatClient`. Each model round trip then
runs as a Temporal Activity with its own timeout and retries, and Temporal records its result in the Workflow's Event
History.

The agent's own function-invocation loop, tools, middleware, context providers and approvals run in the Workflow. After
a crash or a Worker restart, Temporal replays the Workflow from Event History and the agent resumes after the last
completed Activity instead of starting over.

<ReleaseNoteHeader type="prerelease" />

Code snippets in this guide are taken from the
[Agent Framework plugin samples](https://github.com/temporalio/samples-python/tree/main/agent_framework_plugin). Refer to
the samples for the complete code.

## Get started

Install the plugin, then run one agent inside a Workflow.

**Prerequisites**

- This guide assumes you are familiar with Microsoft Agent Framework. If you are not, start with the
  [Agent Framework documentation](https://github.com/microsoft/agent-framework).
- If you are new to Temporal, read [Understanding Temporal](/evaluate/understanding-temporal) or take the
  [Temporal 101](https://learn.temporal.io/courses/temporal_101/) course.
- Set up your local development environment by following
  [Set up your local development environment](/develop/python/set-up-your-local-python). Leave the Temporal development
  server running if you want to test your code locally.
- Use Python 3.11 or later. Agent Framework does not support Python 3.10.
- Export `OPENAI_API_KEY` in the Worker's environment. The samples use OpenAI's `gpt-4o-mini`; the Workflow never sees
  the key.

### Install the plugin

Install the `temporalio-agent-framework` package together with the Agent Framework provider package you use. The
samples use OpenAI:

```bash
uv add "temporalio-agent-framework[mcp]" agent-framework-openai
```

or with pip:

```bash
pip install "temporalio-agent-framework[mcp]" agent-framework-openai
```

The package depends on `agent-framework-core`, not the `agent-framework` meta package, so it does not install every
provider. The `mcp` extra adds `temporalio-mcp` and MCP Python SDK 2.2 or later; leave it out if your agents do not use
MCP servers or your project still pins MCP SDK 1. Refer to the
[package requirements](https://github.com/temporalio/ai-integrations/blob/main/python/agent_framework/pyproject.toml) for
the supported Python, Temporal SDK and Agent Framework versions.

Import `AgentFrameworkPlugin`, `TemporalChatClient` and `TemporalMCPToolProvider` from `temporalio.agent_framework`, and
`activity_as_tool` from `temporalio.agent_framework.workflow`.

### Run an agent with Durable Execution

The following example runs one `Agent` inside a Workflow. The Workflow carries the model name `"gpt-4o-mini"` and
nothing else; the Worker maps that name to a real chat client.

**1. Define the Workflow**

Build the `Agent` over a `TemporalChatClient` instead of a provider client. Each round trip to the model runs as the
`agent_framework.invoke_model` Activity with the Activity options you pass to the client. The sample sets a 60-second
`start_to_close_timeout`. The defaults are a 5-minute `start_to_close_timeout` and a 10-second `heartbeat_timeout`; the
Activity heartbeats on its own at half that interval, so Temporal notices a Worker that died mid-call within seconds.

**2. Start a Worker**

`AgentFrameworkPlugin(chat_clients=...)` maps each model name to a factory that builds the provider's chat client. The
factory runs on the Worker on first use and its client is cached for the Worker's lifetime, so `OPENAI_API_KEY` and the
connection stay on the Worker. Temporal retries the model Activity, so turn the OpenAI SDK's own retries off with
`AsyncOpenAI(max_retries=0)`; `OpenAIChatClient` has no `max_retries` setting of its own. A client that still retries
gets one warning in the Worker log the first time it runs.

Add the plugin to `Client.connect(...)` or to the `Worker`, not both. A Worker inherits the plugins of the Client it is
built from, and a second copy registers the model Activities twice, which the Worker rejects with a `ValueError`. The
plugin registers the `agent_framework.invoke_model` and `agent_framework.invoke_model_streaming` Activities, sets the
Pydantic data converter, and configures the Workflow sandbox for Agent Framework, so the Worker needs no other wiring.

## Build the agent

Choose where each tool runs, connect MCP servers, and add middleware.

### Run tools as Activities

Decide per tool where it runs. A tool that is pure logic stays in the Workflow as an ordinary `@tool`. A tool that does
I/O or reads a clock belongs in an Activity: decorate the function with `@activity.defn`, register it on the Worker, and
pass it to the agent through `activity_as_tool`. The plugin cannot tell the two apart, so the choice is yours.

### Connect to MCP servers

MCP support runs on [`temporalio-mcp`](/develop/python/integrations/mcp) and MCP Python SDK 2, installed by the `mcp`
extra. `AgentFrameworkPlugin(mcp_clients=...)` maps a server name to a factory that returns an `mcp.Client`, the same
shape as `chat_clients`. For each server the plugin registers the `temporalio.mcp.<server>.list-tools` and
`temporalio.mcp.<server>.call-tool` Activities, plus `temporalio-mcp`'s prompt and resource operations
(`list-prompts`, `get-prompt`, `list-resources`, `list-resource-templates`, `read-resource`). The connection lives on
the Worker: the plugin connects on the first MCP Activity and closes the connection after 5 minutes of idleness
(`mcp_connection_idle_timeout`).

In the Workflow, `TemporalMCPToolProvider("echo")` is an Agent Framework context provider. Before each `agent.run` it
lists the server's tools through the `list-tools` Activity and adds one tool per entry, with the server's input schema;
`cache_tools=True` lists once per provider instance instead. Each call the model makes runs the `call-tool` Activity.
Pass it in `context_providers`, not `tools`. Agent Framework's
`MCPStdioTool`, `MCPStreamableHTTPTool` and `MCPWebsocketTool` hold a live connection, which cannot exist in a Workflow,
so they cannot be used in `tools=`; the provider replaces them.

<!--SNIPSTART python-agent-framework-mcp-workflow-->
<!--SNIPEND-->

by changing the factory:

The Activity options on the provider apply to its list and call Activities. The sample sets a 30-second
`start_to_close_timeout`; without one, `temporalio-mcp`'s one-minute default applies. The default Retry Policy retries
without limit, so a run waits while its server is down; bound it with `retry_policy` or `schedule_to_close_timeout`.
MCP Activities do not heartbeat. `tool_name_prefix`, `allowed_tools` and `approval_mode` work as they do on Agent
Framework's `MCPTool`. A server tool whose name the agent already has fails the Workflow with
`AgentFrameworkWorkflowError` before the model call; give that provider a `tool_name_prefix` or an `allowed_tools` list.

### Add middleware

Agent, chat and function middleware run where they run natively: agent middleware in the `Agent`, chat and function
middleware in `TemporalChatClient`. All of it runs in the Workflow, next to the agent's loop. In the sample,
`BlockOutsideTmp` is function middleware that refuses `delete_file` calls outside `/tmp` by setting `context.result`
without calling `call_next()`, so the tool never runs and the model reads the refusal. `AppendReminder` is chat
middleware that adds one sentence to the instructions of every model call before the request leaves for the Activity.

<!--SNIPEND-->

:::caution

A Workflow Definition must be [deterministic](/workflow-definition#deterministic-constraints), and middleware is part
of it. Do not read the clock, do I/O or draw random numbers in middleware. Middleware that needs I/O calls
`await workflow.execute_activity(...)`. Context providers run in the Workflow too and may await Activities in
`before_run` and `after_run`.

:::

Agents compose the same way. `Agent.as_tool()` turns a sub-agent into a tool of a coordinator; every agent runs in the
Workflow and every agent's model calls are Activities, so the whole tree is durable with no per-agent wiring. A
sub-agent called through `as_tool()` runs streaming, so its calls are `agent_framework.invoke_model_streaming`
Activities. The [multi-agent sample](https://github.com/temporalio/samples-python/tree/main/agent_framework_plugin/multi_agent)
gives each agent its own `TemporalChatClient` with a `summary`, so the Activities read `coordinator`, `researcher` and
`writer` in the Web UI.

## Add human approval to tool calls

Approvals are Agent Framework's own. A tool with `approval_mode="always_require"` does not run; `agent.run` returns with
the request in `response.user_input_requests`, and you answer with `request.to_function_approval_response(approved)` on
the same session. In a Workflow the wait is durable. The sample publishes the pending requests through a
[Query](/develop/python/workflows/message-passing#queries), waits in `workflow.wait_condition` for a `decide`
[Update](/develop/python/workflows/message-passing#updates), and runs the agent again with the decision. Only an
approved call runs the tool; a rejected call sends the model Agent Framework's rejection result.

<!--SNIPSTART python-agent-framework-human-in-the-loop-workflow-->
<!--SNIPEND-->

Agent Framework keys the approval by the function call's id and binds the response to the request recorded in the
session, so both runs use the same session. When a provider omits the id, the provider's client assigns one on the
Worker before the response enters Event History, so the id in a pending request survives a Worker restart and a replay.
The Update validator checks the input, `approve` or `reject`, and not the Workflow's state. Validators run before the
Workflow coroutine applies the other events of the same Workflow Task, so a validator that looks for a pending request
would reject a decision that arrives in the same task as the model's reply.

## Stream agent output

`agent.run(prompt, stream=True)` works as it does natively: the `agent_framework.invoke_model_streaming` Activity
consumes the provider's stream and the Workflow receives the updates once the Activity completes. To forward updates to a
consumer outside the Workflow while the call runs, host a [Workflow Stream](/develop/python/workflows/workflow-streams)
on the Workflow and pass `streaming_topic` to `TemporalChatClient`. The Activity publishes each `ChatResponseUpdate`, in
its `to_dict()` form, to that topic, batched every 100 milliseconds (`streaming_batch_interval`). Without `stream=True`
the call runs as the plain model Activity and publishes nothing.

The durable result is the same as without streaming. One streamed call records, as its Activity result, one entry per
function call, usage or finish update and one entry per run of text, so a long answer does not add one Event History
entry per token; the topic still receives every update. If the updates cannot all be published, the Activity fails with
an `ApplicationError` of type `agent_framework.StreamError`. It is non-retryable when a retry would fail the same way,
such as a batch over the 2 MiB payload limit; other publish failures are retried, and the retry calls the model again.

## Keep long conversations under the history limit

Temporal owns the conversation by default. `TemporalChatClient` does not store conversations on the provider's side, so
Agent Framework keeps the transcript in the session's in-memory history and resends it on every call. Event History is
the durable record and replay rebuilds the session.

Every turn adds events. When `workflow.info().is_continue_as_new_suggested()` turns `True`, serialize the session with
`session.to_dict()` and hand it to a fresh run with [Continue-As-New](/develop/python/workflows/continue-as-new); the new
run restores it with `AgentSession.from_dict`. The dict carries the transcript, pending approval state and the
provider's conversation id. The `Agent` object, provider connections and spans do not cross; build the agent again in
the new run.

In the sample each user turn is an Update, so the caller gets the reply from the same call. The `run` method waits until
the chat ends or Temporal suggests Continue-As-New, lets in-flight Updates finish with
`workflow.all_handlers_finished`, and continues as new with the serialized session:

<!--SNIPSTART python-agent-framework-continue-as-new-workflow-->

To let the provider keep the conversation instead, pass `store=True` in the agent's `default_options` or a run's
`options`. The returned conversation id lands in `session.service_session_id`, the next call carries it, and only the
new turn crosses the Activity boundary.

## Compose with an observability plugin

`OpenTelemetryPlugin` composes with `AgentFrameworkPlugin` on the same Client, and the Worker inherits both in
registration order. Agent Framework starts its `invoke_agent` span from Workflow code through the global tracer
provider, so that provider must be replay-safe: set `temporalio.contrib.opentelemetry.create_tracer_provider()` as the
global provider before connecting the Client. With a plain OpenTelemetry SDK `TracerProvider` every replay re-emits the
agent spans, and the plugin warns at Worker and Replayer start. Agent Framework records tool metrics the same way, so
wrap a metrics provider in `ReplaySafeMeterProvider`. The provider client's own `chat` span runs inside the Activity with
real timings.

<!--SNIPSTART python-agent-framework-open-telemetry-worker-->
<!--SNIPEND-->

The sample's `install_tracer_provider` builds that provider with an OTLP exporter. One trace then runs from the
starter's root span through `RunWorkflow:TracedWorkflow`, `invoke_agent assistant` and
`RunActivity:agent_framework.invoke_model` to the OpenAI client's `chat gpt-4o-mini` span. See
[Set up tracing](/develop/python/platform/observability#tracing) for the plugin's options.

## Runtime behavior and limitations

- **Temporal owns retries.** Model calls retry under the `retry_policy` on `TemporalChatClient`; Activity tools and
  MCP providers take their own. Provider errors are classified by HTTP status: 408, 409, 429 and 5xx stay retryable and
  honor `retry-after` headers through the next retry delay, other 4xx are non-retryable, and errors without a status,
  such as connection failures, stay retryable. The failure reaches the Workflow as an `ActivityError` whose cause is an
  `ApplicationError` with `type` set to the provider SDK's exception class name, such as `RateLimitError` or
  `AuthenticationError`. Match on `type`, not on the message.
- **Credentials and clients stay on the Worker.** The Workflow carries a model name. A name no Worker on the Task Queue
  knows fails the Activity with a non-retryable `ApplicationError` of type `AgentFrameworkUnknownChatClient`, so during a
  rolling deployment add a new name to every Worker before Workflows use it. Calling a `TemporalChatClient` outside a
  Workflow raises `RuntimeError`.
- **What crosses the Activity boundary.** Messages and chat options cross in their `to_dict()` form, tools as their
  JSON schema specs, and the `ChatResponse` comes back the same way; provider SDK objects never enter Event History. A
  run's `client_kwargs`, such as `extra_headers`, reach the provider client when they are JSON-compatible. Hosted tools
  passed as mappings, such as a provider's web search, run on the provider's side. A tool object the plugin cannot send
  to the model fails the Workflow with `AgentFrameworkWorkflowError`.
- **Sandbox and clocks.** The plugin passes `agent_framework`, `pydantic_core`, `annotated_types`, `msgspec`,
  `typing_inspection`, `opentelemetry`, `dotenv`, `mcp` and `mcp_types` through the Workflow sandbox, and installs
  Workflow-aware stand-ins for the clock and id reads in Agent Framework's agent code (default agent and session ids,
  the loop's time budget, span durations) so they replay deterministically. Workers and Replayers both get them. A
  Worker fails at start, naming the seam and the installed version, if an Agent Framework release moves one of them.
- **Framework exceptions fail the Workflow.** Agent Framework's own exceptions raised in Workflow code, such as
  `MiddlewareFailure`, and `AgentFrameworkWorkflowError` are registered as Workflow failure types, because retrying the
  Workflow Task cannot change a deterministic failure.
- **File-backed persistence does not work in a Workflow.** `FileHistoryProvider`, `FileSessionStore` and
  `SessionStore` read and write files on a thread, which the Workflow event loop does not provide, so the first run
  fails. Use the default in-memory history and carry `session.to_dict()` across Continue-As-New, or pass `store=True`
  to let the provider keep the conversation.
- **Synchronous tools block the Workflow Task** while they run. Keep them quick or make them Activities.
- **Not in this release.** The Agent Framework Workflows pillar (`WorkflowBuilder`, executors, checkpoints,
  `agent-framework-orchestrations`), the harness, skills, evaluations, DevUI, declarative agents, hosting, memory and
  vector providers, and the experimental agent hooks are out of scope. Compose agents with Temporal Workflow code
  instead: `Agent.as_tool()`, Signals, Timers and Child Workflows. OpenAI background responses (`continuation_token`)
  and embedding clients are not routed through Activities.
