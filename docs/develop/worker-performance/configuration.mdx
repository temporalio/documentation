Each Worker can be configured by providing custom Worker options (`WorkerOptions`) at instantiation.
Options are specific to individual Workers and do not affect other members of your fleet.

## Executor slot options

The `maxConcurrentWorkflowTaskExecutionSize` and `maxConcurrentActivityExecutionSize` options define the number of total available Workflow Task and Activity Task slots for a Worker.

:::caution

- Worker tuners supersede the existing `maxConcurrentXXXTask` style Worker options.
  Using both styles will cause an error at Worker initialization time.

:::

## Configuring poller options {/* #configuring-poller-options */}

### Recommended approach

The Temporal SDKs support Poller Autoscaling, which automatically selects an appropriate number of pollers based on need. Using this feature results in more efficient poller usage, better throughput, and schedule-to-start latency improvements.

Poller Autoscaling does not change your Worker count, compute capacity, or task execution limits.

:::tip

`PollerBehaviorAutoscaling` is only enabled in Temporal Server v1.28.0 and later.

:::

### Poller Autoscaling by default in Temporal Cloud

Temporal Cloud is enabling Poller Autoscaling by default for all Namespaces in stages.
After Poller Autoscaling is enabled for your Namespace, Workers on a supported SDK version use it for every poller type whose poller count and poller behavior options are unset.
Poller Autoscaling replaces the SDK's fixed default poller counts for those poller types, with no configuration change required.
The change takes effect the next time each Worker starts. Workers that are already running keep their current polling behavior until they restart.

To check whether a Worker uses Poller Autoscaling, select the Worker on the Workers tab in the Temporal UI, or call the [DescribeWorker](https://api-docs.temporal.io/#temporal.api.workflowservice.v1.WorkflowService.DescribeWorker) API.

The following SDK versions use Poller Autoscaling by default when it's enabled for the Namespace:

| SDK | Minimum version |
| --- | --- |
| Go | [1.47.0](https://github.com/temporalio/sdk-go/releases/tag/v1.47.0) |
| Java | [1.38.0](https://github.com/temporalio/sdk-java/releases/tag/v1.38.0) |
| Python | [1.36.0](https://github.com/temporalio/sdk-python/releases/tag/1.36.0) |
| .NET | [1.22.0](https://github.com/temporalio/sdk-dotnet/releases/tag/1.22.0) |
| Ruby | [1.11.0](https://github.com/temporalio/sdk-ruby/releases/tag/v1.11.0) |
| Rust | [0.6.0](https://github.com/temporalio/sdk-rust/releases/tag/v0.6.0) |

The TypeScript SDK release that uses Poller Autoscaling by default is not yet available.
To use Poller Autoscaling with the currently released TypeScript SDK, [enable it explicitly](#enable-poller-autoscaling-explicitly).

Explicit poller settings are preserved, including a poller count explicitly set to the SDK's default value.
Temporal applies the default separately to Workflow, Activity, and Nexus Task pollers.
For example, if you configure a fixed Workflow Task poller count, Workflow Task pollers stay fixed, while Activity and Nexus Task pollers with unset options use Poller Autoscaling.

### Enable poller autoscaling explicitly

You can enable Poller Autoscaling in your Worker by setting the `*_task_poller_behavior` options to `PollerBehaviorAutoscaling`.
Names vary by SDK; see the [SDK examples](#sdk-examples) below.
Use this approach when Poller Autoscaling isn't yet enabled for your Namespace, when your SDK version doesn't use it by default, or when you connect to a self-hosted Temporal Service that supports Poller Autoscaling.

### Retain fixed poller settings {/* #manual-configuration */}

To keep fixed poller counts after Poller Autoscaling is enabled for your Namespace, explicitly configure a fixed poller count or a fixed poller behavior for each poller type you want to keep fixed, then restart your Workers.
The fixed behavior is named `PollerBehaviorSimpleMaximum` or `PollerBehavior.SimpleMaximum` in most SDKs, and uses `type: 'simple-maximum'` in TypeScript.
Refer to your SDK's API reference in the [SDK examples](#sdk-examples) below for its configuration options.

Poller Autoscaling also provides minimum, maximum, and initial poller counts.
In every SDK, the defaults are a minimum of 1, an initial count of 5, and a maximum of 100 pollers for each poller type.
Temporal recommends using these default bounds for most workloads rather than manually tuning them.

## Cache options (Java SDK) {/* #cache-options */}

A [Workflow Cache](/workflow-execution#workflow-cache) is created and shared between all Workers on a single host.
It's designed to limit the resources used by the cache for each host/process.
These options are defined on `WorkerFactoryOptions`:

- `WorkerFactoryOptions#workflowCacheSize` defines the maximum number of cached Workflow Executions.
  Each cached Workflow contains at least one Workflow thread and its resources (memory, etc.).
- `maxWorkflowThreadCount` defines the maximum number of Workflow threads that may exist concurrently at any time.

These cache options limit the resource consumption of the in-memory Workflow cache.
Workflow cache options are shared between all Workers because the Workflow cache is tightly integrated with the resource consumption of the entire host.
This includes memory and the total thread count, which should be limited per host/JVM.

For Go, use [`SetStickyWorkflowCacheSize`](https://pkg.go.dev/go.temporal.io/sdk/worker#SetStickyWorkflowCacheSize). For Python, use the `max_cached_workflows` Worker option.

## "Large value" drawbacks

There are drawbacks when you use "large values everywhere."
As with any multithreading system, specifying excessively large values without monitoring with the SDK and system metrics leads to constant resource contention/stealing
This decreases the total throughput and increases latency jitter of the system.

## Invariants (JavaSDK only) {/* #invariants */}

These properties should always be true for a Worker's configuration.

Perform this sanity check after the adjustments to Worker settings.

1. `workflowCacheSize` should be ≤ `maxWorkflowThreadCount`. Each Workflow has at least one Workflow thread.
2. `maxConcurrentWorkflowTaskExecutionSize` should be ≤ `maxWorkflowThreadCount`. It's recommended that `maxWorkflowThreadCount` be at least 2x of `maxConcurrentWorkflowTaskExecutionSize`. This is because having more Worker slots than the Workflow cache size will lead to resource allocation issues between executors and cause unpredictable delays.
3. `maxConcurrentWorkflowTaskPollers` should be significantly ≤ `maxConcurrentWorkflowTaskExecutionSize`. And `maxConcurrentActivityTaskPollers` should be significantly ≤ `maxConcurrentActivityExecutionSize`. The number of pollers should always be lower than the number of executors.
