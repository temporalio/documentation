Temporal Cloud provides built-in Endpoint access controls and secure connectivity across Namespaces.
Self-hosted deployments can implement [custom Authorizers](/self-hosted-guide/security#authorizer-plugin).

## Runtime access controls {/* #runtime-access-controls */}

In Temporal Cloud, each Endpoint has an access control policy: an allowlist of caller Namespaces.

<CaptionedImage
    src="/img/cloud/nexus/nexus-workers-short.png"
    title="Nexus Security"
/>

Workers authenticate with their Namespace using mTLS or API key.
When a caller Workflow executes a Nexus Operation, Temporal Cloud verifies the caller's Namespace is in the Endpoint's allowlist before routing the request to the handler.
Temporal Cloud acts as a trusted broker across Namespace boundaries.

See [Configure runtime access controls](/nexus/registry#configure-runtime-access-controls).

## Secure connectivity {/* #secure-connectivity */}

:::info

Temporal Cloud has built-in secure connectivity across all Namespaces in an Account.

Self-hosted deployments rely on the Temporal Cluster being secure.

:::

Temporal Cloud secures all Nexus communication:

- Workers authenticate to their Namespace using mTLS or API key.
- mTLS encrypts all cross-Namespace Nexus traffic (start, cancel, and completion callbacks) across cells and regions.
- Endpoints are only accessible from within a Temporal Cloud Account through the Temporal SDK - not externally accessible.

## Payload encryption and Data Converter {/* #payload-encryption-data-converter */}

Nexus uses the same Data Converter as Workflows and Activities - JSON, Proto, and binary payloads are all supported.
If you use a Codec for encryption, it also encrypts Nexus payloads.

Caller and handler Workers must have compatible Data Converters.
Payloads are encrypted by the sender (caller encrypts input, handler encrypts result).

### Nexus serialization context {/* #nexus-serialization-context */}

When the Data Converter encodes or decodes a Nexus payload, it receives a Nexus serialization context with the Nexus Endpoint name, Service name, and Operation name.
A Payload Codec, Payload Converter, or Failure Converter that supports serialization context can use these values, for example to select an encryption key for each Endpoint.

The context covers the Operation's own payloads and the payloads that the handler's Workflows, Updates, and Standalone Activities return to the caller:

| Payload | Serialization context |
| --- | --- |
| Operation input, synchronous result, and failure | Nexus |
| Result and closing failure of a Workflow started by the handler | Nexus |
| Input, Memo, Signals, and Queries of a Workflow started by the handler | Workflow |
| Result, failure, and rejection of an Update sent by the handler | Nexus |
| Arguments of an Update sent by the handler | Workflow |
| Result, failures, and Heartbeat details of a Standalone Activity started by the handler | Nexus |
| Input of a Standalone Activity started by the handler | Activity |

The Temporal Service stores the context with the Workflow Execution, Update, Standalone Activity, or Standalone Nexus Operation, and returns it to Clients that read results later.
A handle you get by ID decodes the result with the same context the caller uses.

To complete a Standalone Activity started by a Nexus handler [asynchronously](/activity-execution#asynchronous-activity-completion), read the Nexus serialization context from the Activity info and pass it to the Client that completes the Activity.
The completing Client only has the Task Token, so it can't get the context any other way.

:::warning Don't share IDs across Endpoints with `USE_EXISTING`

If a Nexus handler uses the `USE_EXISTING` conflict policy and an execution (Workflow or Standalone Activity) with that ID is already running, the handler attaches to it instead of starting a new one.
The result keeps the context of whatever started that execution.
If a different Endpoint started it, or it didn't start from a Nexus handler at all, the caller's codec can pick the wrong key and fail to decode the result.

To avoid this, use Workflow IDs and Activity IDs that are unique to each Endpoint, and don't start executions with those IDs outside the handler.
Standalone Nexus Operations started with `USE_EXISTING` behave the same way.

:::

### Choose a cross-Namespace encryption approach {/* #choose-encryption-approach */}

Three common approaches for cross-Namespace payload encryption:

#### Option 1: Same encryption key {/* #same-encryption-key */}

Both Namespaces share the same encryption key.
This approach needs no additional configuration.

#### Option 2: Pass KMS key ID in payload metadata {/* #kms-key-id-metadata */}

Each Namespace uses its own encryption key, with the KMS key ID passed in Temporal payload metadata.
The receiver reads the key ID from metadata and decrypts using KMS IAM permissions.

This works in both directions: the caller encrypts input with the caller's key, and the handler decrypts using the key ID from metadata, then encrypts the result with the handler's key.
The Codec Server needs KMS decrypt permissions for all relevant keys.

See the [encryption sample](https://github.com/temporalio/samples-go/blob/main/encryption/data_converter.go) and the [reference-app-orders-go data converter](https://github.com/temporalio/reference-app-orders-go/blob/main/app/temporalutil/data_converter.go).

#### Option 3: Endpoint-specific encryption keys {/* #endpoint-specific-keys */}

Use the [Nexus serialization context](#nexus-serialization-context) to select an encryption key for each Nexus Endpoint in your Payload Codec.
This encrypts Nexus traffic with a dedicated key, without sharing Namespace keys across teams.
Because Workflows, Updates, and Standalone Activities started by the handler encode their results with the same context, the caller can decode them with the Endpoint's key.

Record the key ID in payload metadata as well, so the codec can decode payloads that were encoded without context, such as payloads from executions that started before the Temporal Service supported it.

#### Compare the approaches {/* #compare-encryption-approaches */}

Options 1 and 2 work with the standard Data Converter.
Option 3 needs a Payload Codec that uses serialization context, and is intended for teams that don't want to share their Namespace encryption keys with other teams.
