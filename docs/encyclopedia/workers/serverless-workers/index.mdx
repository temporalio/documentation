## What is a Serverless Worker? {/* #serverless-worker */}

A Serverless Worker is a Temporal Worker that runs on serverless compute instead of a long-lived process. There is no
always-on infrastructure to provision or scale. You configure a compute provider, and Temporal starts and stops Workers
in response to work on a Task Queue.

A Serverless Worker uses the same Temporal SDKs as a traditional long-lived Worker, and registers Workflows and
Activities the same way. What differs is that Temporal manages the Worker's lifecycle rather than you running a Worker
process. How that lifecycle works depends on the compute provider: AWS Lambda runs short-lived invocations, Amazon
Bedrock AgentCore Runtime runs sessions with idle and maximum-lifetime limits, and GCP Cloud Run runs a pool of
long-lived instances. See [Worker lifecycle](#worker-lifecycle).

Serverless Workers require [Worker Versioning](/worker-versioning). Each Serverless Worker must be associated with a
[Worker Deployment Version](#worker-deployment-versions) that has a [compute configuration](#compute-configuration).

To deploy a Serverless Worker, see
[Deploy a Serverless Worker](/production-deployment/worker-deployments/serverless-workers).

### Worker Deployment Versions {/* #worker-deployment-versions */}

A **Worker Deployment Version** represents one build of your Workers within a Worker Deployment. The Worker Deployment
name and Build ID identify the version within a Namespace.

Configure each Worker with its Task Queue, Worker Deployment name, and Build ID. When the Worker polls, Temporal
associates that Task Queue with the Worker Deployment Version. Other Workers using the same version can poll the same
queue or additional queues. All Workers in the version run the same Worker build.

Temporal tracks information associated with each version:

- **Task Queues:** the queues registered when its Workers poll.
- **Rollout status:** whether it is the Current or Ramping Version and its ramp percentage.
- **Drainage status:** whether open pinned Workflows still need the version.
- **Metadata and timestamps:** user-provided information, creation time, and routing changes.
- **Compute configuration (optional):** how Temporal starts and scales Serverless Workers for the version.

A version identifies the Worker build; you deploy that build to your compute provider. Keep the build fixed for the
version even when changing its compute configuration. For rollout and pinning behavior, see
[Worker Versioning](/worker-versioning).

### Compute configuration {/* #compute-configuration */}

A **compute configuration** tells Temporal how to start and scale Workers for a Worker Deployment Version. Serverless
Workers require it. Traditional long-lived Workers can use Worker Deployment Versions without compute configuration
because you start and manage those Worker processes yourself.

The compute configuration contains one or more named **scaling groups**. Each group describes a compute target and its
scaling settings.

#### Scaling groups {/* #scaling-groups */}

The standard single-region setup creates one group named `default`, pointing at your Lambda function or Cloud Run
Worker Pool. The compute resource has a region: the AWS region in the function ARN, or the GCP region of the pool.
That compute region can differ from the Namespace's active region within the same cloud provider.

By default, the single-region UI and CLI setup leave the group's region scope unset. With only this unscoped group, the
[Worker Controller Instance (WCI)](#worker-controller-instance) uses its compute target regardless of which region in
the same cloud provider is active for the Namespace. The group does not inherit a restriction from the Namespace's
current region.

For example, a Namespace active in `aws-us-east-1` can use a `default` group pointing at a Lambda in `us-east-1`. If the
Namespace fails over to `aws-us-west-2`, the WCI keeps invoking that same Lambda in `us-east-1`. The unscoped group
continues to apply, but its function remains in its original region.

Each group has these settings:

| Setting | Purpose |
| --- | --- |
| Compute provider | Identifies the function or Worker Pool and the credentials Temporal uses to invoke or scale it. |
| Scaling settings | Tune provider-specific behavior, such as Lambda invocation cooldowns or Cloud Run instance limits and utilization targets. |
| Region scope (optional) | Restricts the group to specific active Namespace regions. By default, a single-region setup leaves this unset, so the group continues to apply if the Namespace changes regions. |

The compute provider determines the autoscaling algorithm. You tune that algorithm's behavior through the provider's
scaling settings. See [Autoscaling](#autoscaling) for the behavior of each provider.

For regional failover, add a group whose region scope matches the Namespace's replica region and whose compute target
is deployed there. When that region becomes active, the WCI uses the matching group instead of the unscoped
group. See [High Availability](#high-availability) for selection rules and setup guides.

In the Temporal Cloud UI, configuring compute under the replica's region card supplies that region association for
you. In the CLI, use `--region-id` to specify it.

The CLI's `--scaling-group` flag selects an entry by name. A group named `default` can also have an explicit region
scope; the name does not determine its scope or the compute resource's location.

The same WCI manages all groups in a Worker Deployment Version; adding a group does not create another version or WCI.

### Compute providers {/* #compute-providers */}

A compute provider is the part of a scaling group that tells Temporal how to invoke or scale Serverless Workers. It
specifies the provider type, the compute target, and the credentials Temporal needs to manage that compute.

For example, an AWS Lambda compute provider includes the Lambda function ARN and the IAM role Temporal assumes to invoke
it. A GCP Cloud Run compute provider includes the Worker Pool's project, region, and name, and the service account
Temporal impersonates to scale it.

Compute providers are only needed for Serverless Workers. Traditional long-lived Workers do not require a compute
provider because the Worker process lifecycle is not managed by the Temporal server.

Temporal supports three compute providers:

| Provider                       | Description |
| ------------------------------ | ----------- |
| AWS Lambda                     | Temporal assumes an IAM role in your AWS account to invoke a Lambda function. |
| Amazon Bedrock AgentCore Runtime | Temporal assumes an IAM role in your AWS account to invoke an AgentCore Runtime endpoint. |
| GCP Cloud Run                  | Temporal scales a Cloud Run [Worker Pool](https://cloud.google.com/run/docs/resource-model#worker-pools) through the Cloud Run admin API. A Worker Pool is its own Cloud Run resource type, distinct from a Service or a Job. |

## How Serverless invocation works {/* #how-invocation-works */}

With long-lived Workers, you start the Worker process, which connects to Temporal and polls a Task Queue for work.
Temporal does not need to know anything about the Worker's infrastructure.

With Serverless Workers, Temporal starts the Worker.

### Worker Controller Instance {/* #worker-controller-instance */}

The Worker Controller Instance (WCI) is a system Workflow that scales Serverless Workers based on Task Queue conditions.
One WCI Workflow runs per Worker Deployment Version that has a compute configuration. It manages all of that version's
[scaling groups](#scaling-groups) and runs in the same Namespace as your Worker Deployment.

A Namespace runs at most 100 WCI Workflows by default, which caps how many Worker Deployment Versions in the Namespace
can have a compute provider at once. A version's WCI runs until the version is deleted, so drained versions count
against the limit. See
[Max Worker Controller Instances limits](/evaluate/cloud/limits#max-worker-controller-instances-limits).

The WCI adjusts the Worker count based on Task Queue conditions. Sync match failures and Task Queue backlog signal that
more capacity is needed, and the WCI adds Workers by triggering the configured compute provider. It also removes
capacity as work drains. How often the WCI re-evaluates the count, and how it sizes the pool, depends on the compute
provider. For details, see [Autoscaling](#autoscaling).

You can list WCI Workflows in your Namespace:

```bash
temporal workflow list \
  --namespace <NAMESPACE> \
  --query 'TemporalNamespaceDivision = "TemporalWorkerControllerInstance"'
```

WCI Workflow IDs follow the pattern `temporal-sys-worker-controller-instance:<deployment-name>:<build-id>`. You can
inspect a WCI Workflow's history to see its recent Activity results:

```bash
temporal workflow show \
  --namespace <NAMESPACE> \
  --workflow-id 'temporal-sys-worker-controller-instance:<DEPLOYMENT_NAME>:<BUILD_ID>'
```

The invocation flow works as follows:

1. A Task is submitted (for example, `StartWorkflow` or `ScheduleActivity`).
2. The [Matching Service](/temporal-service/temporal-server#matching-service) attempts to route the Task directly to an
   available Worker (a sync match).
3. If a Worker is available, the Task is routed to that Worker.
4. If no Worker is available (sync match fails), the Matching Service pushes a signal to the WCI, and the WCI triggers
   the configured compute provider to start a Worker.
5. The Serverless Worker starts, creates a Temporal Client, and begins polling the Task Queue.
6. The Worker processes Tasks from the Task Queue.

:::note

Sync match failure is only one of the signals the WCI acts on. It also reacts to Task Queue backlog, and depending on
the compute provider it periodically re-sizes the pool based on the rate of arriving work. What the WCI monitors and how
it scales differ by provider. See [Autoscaling](#autoscaling).

:::

Whether a Worker handles a single burst of Tasks and exits, or stays running to process Tasks over a long lifetime,
depends on the compute provider's execution model. See [Worker lifecycle](#worker-lifecycle).

## Autoscaling {/* #autoscaling */}

The [WCI](#worker-controller-instance) automatically scales Serverless Workers up and down based on Task Queue conditions, including sync match failures and Task Queue backlog.
The autoscaling algorithm differs by compute provider because of differences in cold start latency, invocation duration limits, and provider APIs.
Refer to the autoscaling section for your compute provider:

- [AWS Lambda autoscaling](/serverless-workers/aws-lambda#autoscaling)
- [GCP Cloud Run autoscaling](/serverless-workers/cloud-run#autoscaling)

## Scaling with long-lived Workers {/* #scaling-with-long-lived-workers */}

Serverless Workers can share a Task Queue with long-lived Workers. What the WCI does with the Tasks the long-lived
Workers are already handling depends on the compute provider, and so does the guidance. Refer to the section for your
compute provider:

- [AWS Lambda](/serverless-workers/aws-lambda#sharing-a-task-queue)

## Failure handling {/* #failure-handling */}

Serverless Workers rely on Temporal's standard retry and timeout semantics to recover from failures. The following
sections describe common failure scenarios and how they are handled.

### Worker crash {/* #worker-crash */}

If a Worker crashes (out of memory, unhandled exception, etc.), the behavior follows standard Temporal retry semantics:

- The Activity Timeout fires after the configured duration.
- Temporal retries the Activity on another Worker.
- No manual intervention is required.

### Provider concurrency limit {/* #provider-concurrency-limit */}

If the compute provider's capacity limit is reached (for example, AWS Lambda account concurrency or a GCP Cloud Run
maximum instance count):

- The WCI cannot add Workers beyond the limit.
- Tasks remain in the Task Queue backlog. No data loss occurs.
- Processing slows until capacity frees up.

### Resource exhaustion across Activity slots {/* #resource-exhaustion */}

By default, a single Worker may run multiple Activity slots. A crash or resource exhaustion in one Activity
(for example, out-of-memory from a memory-intensive operation) can affect other Activities running on the same Worker.

To isolate Activities from each other:

- Split Workflow Workers and Activity Workers into separate Worker Deployments.
- Set Activity slots to 1 per Worker.

With single-slot configuration, each Activity gets a dedicated execution environment.

## High Availability {/* #high-availability */}

[Temporal Cloud High Availability](/cloud/high-availability) replicates a Namespace and manages its failover.
Serverless Worker compute configuration determines where Temporal starts Workers after that failover. These are
separate parts of recovery: a healthy Namespace still needs available compute and application dependencies to process
work.

The WCI runs where the Namespace is active. A [scaling group's](#scaling-groups) `region_ids` names the Temporal regions where
that group applies. After Namespace failover, the WCI selects compute for the newly active region.

The compute resource's location is configured separately, in a Lambda ARN or a Cloud Run Worker Pool's region. Assigning
a group to a Namespace region does not deploy or move compute there. Two groups pointing at the same compute region
retain a dependency on that region.

### Regional and default compute configurations

For the configurations in the provider setup guides, regional selection works as follows:

| Configuration | Behavior |
| --- | --- |
| A scaling group matches the active region. | The WCI uses that region's group. |
| No regional group matches, but an unscoped group exists. | The WCI uses the unscoped group's compute target, even if that target is in another region. |
| Neither a matching group nor an unscoped group exists. | The WCI starts no compute for that region. Tasks wait for Workers that can serve the version. |

Existing single-region groups remain unscoped until you configure a region scope. They can keep serving work after a
Namespace-only failover if their compute remains healthy, but do not protect against losing the compute region.

Regional selection also supports traditional Workers in the primary region and Serverless Workers only in the recovery
region. Both use the same Worker Deployment Version; a group scoped only to the recovery region starts Serverless
Workers when the Namespace becomes active there.

### Existing Workers after failover

Regional compute selection changes where new Workers start. It does not immediately prevent Workers already running
in the original region from receiving Tasks. Healthy Workers can reach the new active Namespace through the Namespace
Endpoint or [request forwarding](/cloud/high-availability#request-forwarding).

Those Workers also need access to their application dependencies. A Worker might still reach Temporal Cloud while its
regional database is unavailable. Regional Endpoints with
[passive poller forwarding disabled](/cloud/high-availability/enable#change-forwarding-behavior) prevent new Tasks from
being delivered through the passive replica. This setting does not terminate running Activities. Workers using the
Namespace Endpoint can follow the active replica regardless of their compute location.

How existing compute stops depends on the provider:

- [AWS Lambda](/serverless-workers/aws-lambda#high-availability): existing invocations finish on their own.
- [GCP Cloud Run](/serverless-workers/cloud-run#high-availability): the WCI scales pools that no longer serve the active
  region to zero.

### Namespace and compute outages

Serverless Workers follow Namespace failover; there is no separate Worker failover operation. Temporal Cloud's
automatic failover monitors Temporal Cloud health. A failure limited to Lambda, Cloud Run, or your application does not
automatically trigger Namespace failover.

Regional Serverless compute supports Active/Passive recovery. Configure each Worker Deployment Version that must
continue serving work, including versions used by pinned Workflows. For setup, testing, and provider outage recovery,
see the provider guide:

- [Configure high availability on AWS Lambda](/production-deployment/worker-deployments/serverless-workers/aws-lambda/high-availability)
- [Configure high availability on GCP Cloud Run](/production-deployment/worker-deployments/serverless-workers/cloud-run/high-availability)

## Constraints {/* #constraints */}

| Constraint        | Detail                                                                                                                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Activity duration | Depends on the compute provider. On AWS Lambda, an Activity must finish within the invocation limit (15 minutes maximum), minus the shutdown deadline buffer. On Amazon Bedrock AgentCore Runtime, a microVM session has a maximum lifetime of 8 hours. On GCP Cloud Run, instances are long-lived, so no per-invocation limit applies. See [Worker lifecycle](#worker-lifecycle). |
| Workflow duration | No limit. Workflows of any duration work. A Workflow runs across as many Workers as needed.                                                                                                                           |
| Worker code       | Depends on the compute provider. AWS Lambda uses a serverless Worker package for your SDK. Amazon Bedrock AgentCore Runtime and GCP Cloud Run run standard long-lived Temporal Workers inside provider-specific runtime infrastructure. |
| Versioning        | [Worker Versioning](/worker-versioning) is required. Each Workflow must have an `AutoUpgrade` or `Pinned` behavior, set per-Workflow or as a Worker-level default. See [Worker Versioning](/worker-versioning) for rollout strategies such as ramping, and [Worker Versioning with Serverless Workers](#worker-versioning-with-serverless-workers) for how Worker Deployment Versions map to compute provider primitives. |
| Multi-cloud Replication | Serverless Workers do not support [Multi-cloud Replication](/cloud/high-availability#multi-cloud-replication). They must be invoked from the same cloud provider where the Namespace is currently active. After a failover to a different cloud provider, Serverless Workers can no longer be invoked. This is a temporary restriction during Public Preview. |
| Multi-region Replication | Regional compute configurations let Workers follow Namespace failover within the same cloud provider. Default configurations keep targeting their original compute resources. See [High Availability](#high-availability). |

## Worker Versioning with Serverless Workers {/* #worker-versioning-with-serverless-workers */}

Serverless Workers require [Worker Versioning](/worker-versioning), and the compute provider must invoke a stable,
immutable build for each Worker Deployment Version.
How Worker Deployment Versions map to compute provider primitives differs by provider.
Refer to the versioning section for your compute provider:

- [AWS Lambda versioning](/serverless-workers/aws-lambda#worker-versioning)
- [Amazon Bedrock AgentCore Runtime versioning](/serverless-workers/agentcore#worker-versioning)
