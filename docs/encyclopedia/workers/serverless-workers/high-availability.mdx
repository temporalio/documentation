[Temporal Cloud High Availability](/cloud/high-availability) replicates a Namespace and manages its failover.
By default, when a Namespace fails over to another region in the same cloud provider, Temporal still uses your original
Serverless Worker compute. To let Serverless Workers follow Namespace failover, configure compute in both regions.
After failover, Temporal starts new Workers using the compute configured for the newly active region.

## Compute selection after failover

The [Worker Controller Instance (WCI)](/serverless-workers#worker-controller-instance) runs where the Namespace is
active. A [scaling group's](/serverless-workers#scaling-groups) `region_ids` names the Temporal regions where that group
applies. After Namespace failover, the WCI selects compute for the newly active region.

The compute target specifies where the resource runs, through the region in the Lambda ARN or the Cloud Run Worker
Pool's region setting.

### Example of regional compute selection

A Worker Deployment Version has two scaling groups. Each group points to a Lambda function running the same Worker
build. While the Namespace is active in `aws-us-east-1`, the WCI invokes the function in `us-east-1`. After the
Namespace fails over to `aws-us-west-2`, the WCI invokes the function in `us-west-2` to start new Workers.

If the `aws-us-west-2` scaling group instead points to a Lambda ARN in `us-east-1`, the WCI selects the `aws-us-west-2`
group after failover and still invokes a function in `us-east-1`.

## Regional and default compute configurations

For the configurations in the provider setup guides, regional selection works as follows:

| Configuration | Behavior |
| --- | --- |
| A scaling group matches the active region. | The WCI uses that region's group. |
| No regional group matches, but an unscoped group exists. | The WCI uses the unscoped group's compute target, even if that target is in another region. |
| Neither a matching group nor an unscoped group exists. | The WCI starts no compute for that region. Tasks wait for Workers that can serve the version. |

Existing single-region groups remain unscoped until you configure a region scope. They can keep serving work after a
Namespace-only failover if their compute remains healthy, but do not protect against losing the compute region.

Regional selection also supports traditional Workers in the primary region and Serverless Workers only in the recovery
region. Both use the same Worker Deployment Version. A group scoped only to the recovery region starts Serverless
Workers when the Namespace becomes active there.

## Existing Workers after failover

Regional compute selection changes where new Workers start. It does not immediately prevent Workers already running
in the original region from receiving Tasks. Healthy Workers can reach the new active Namespace through the Namespace
Endpoint or [request forwarding](/cloud/high-availability#request-forwarding).

Those Workers also need access to their application dependencies. A Worker might still reach Temporal Cloud while its
regional database is unavailable. Regional Endpoints with
[passive poller forwarding disabled](/cloud/high-availability/enable#change-forwarding-behavior) prevent new Tasks from
being delivered through the passive replica. This setting does not terminate running Activities. Workers using the
Namespace Endpoint can follow the active replica regardless of their compute location.

How existing compute stops depends on the provider:

- [AWS Lambda](/serverless-workers/aws-lambda#high-availability): existing invocations finish on their own.
- [GCP Cloud Run](/serverless-workers/cloud-run#high-availability): the WCI scales pools that no longer serve the active
  region to zero.

## Namespace and compute outages

Temporal selects regional Serverless Worker compute as part of Namespace failover. Temporal Cloud's automatic failover
monitors Temporal Cloud health. A failure limited to Lambda, Cloud Run, or your application does not automatically
trigger Namespace failover.

Regional Serverless compute supports Active/Passive recovery. Configure each Worker Deployment Version that must
continue serving work, including versions used by pinned Workflows. For setup, testing, and provider outage recovery,
see the provider guide:

- [Configure high availability on AWS Lambda](/production-deployment/worker-deployments/serverless-workers/aws-lambda/high-availability)
- [Configure high availability on GCP Cloud Run](/production-deployment/worker-deployments/serverless-workers/cloud-run/high-availability)
