You can reach Temporal Cloud from anywhere with Internet connectivity, wherever your Namespaces are located, and your applications can run in the cloud environment or data center of your choice.
Create Namespaces in a region close to where you host your Workers to reduce latency.

This page lists supported Temporal Cloud regions and any restrictions on creating Namespaces.

:::tip Service availability

Check the status of supported regions at [status.temporal.io](https://status.temporal.io).
Subscribe there to get an email whenever Temporal creates, updates, or resolves an incident.

:::

## GCP capacity restriction {/* #gcp-capacity-restriction */}

:::caution

New Temporal Cloud Namespace provisioning is temporarily restricted in Iowa (`us-central1`) and Frankfurt (`europe-west3`) due to limited GCP compute capacity.
Provisioning is available to all accounts in Mumbai (`asia-south1`), Jakarta (`asia-southeast2`), Northern Virginia (`us-east4`), and Oregon (`us-west1`).

:::

Existing GCP Namespaces continue to operate.
For Namespaces using [Provisioned Capacity](/cloud/capacity-modes#provisioned-capacity), self-service increases to Temporal Resource Units (TRUs) are disabled in restricted GCP regions.
To request a TRU increase in a restricted region, [create a support ticket](/evaluate/cloud/support#support-ticket) for Temporal Dev Success to coordinate a manual increase, subject to available capacity.
Immediately available TRU inventory is not guaranteed in any region, including regions without restrictions.

If your new Namespace must be in a restricted GCP region, [create a support ticket](/evaluate/cloud/support#support-ticket) to request an exception for your account.
Include the required GCP regions, expected Action volume, and business requirements for your workload.

Multi-Cloud Replication to Mumbai (`asia-south1`), Northern Virginia (`us-east4`), and Oregon (`us-west1`) is available for the [supported region pairs](#gcp-service-regions) without an account exception.
Multi-Region Replication between Northern Virginia (`us-east4`) and Oregon (`us-west1`) is also available without an account exception.
Jakarta (`asia-southeast2`) does not support High Availability features.
To add a replica in a restricted GCP region using Multi-Region Replication or Multi-Cloud Replication, [create a support ticket](/evaluate/cloud/support#support-ticket), even if your account already has an approved exception.
In restricted regions, an approved exception enables self-service creation of single-region GCP Namespaces only; adding a GCP replica still requires assistance from Temporal Dev Success.
Include the full Namespace ID (`<namespace>.<account>`) and destination region for each Namespace in your ticket.
Temporal Dev Success coordinates with the High Availability team to add approved replicas manually.
You can still add an AWS replica to an existing GCP Namespace without an exception, where that replication option is [supported](#gcp-service-regions).
See [Enable and manage High Availability](/cloud/high-availability/enable) for instructions.

You can also deploy new workloads in an [AWS region](#aws-service-regions).

## Azure service regions

<ReleaseNoteHeader featureName="azure">
  Temporal Cloud on Azure is available with rolling access for production workloads.
  The [Temporal Cloud SLA](https://temporal.io/sla) applies during Azure Public Preview.
</ReleaseNoteHeader>

To create Azure Namespaces or add Azure replicas, request access by [creating a support ticket](/evaluate/cloud/support#support-ticket) with Temporal Dev Success.
Include your required regions, expected Actions per second (APS), number of Namespaces, and workload requirements.
Temporal reviews your capacity needs before enabling Azure regions for your account.
Azure regions do not appear in your account until access is enabled.
Access and capacity increases are subject to available capacity.
After access is enabled, create and manage Azure Namespaces in the Temporal Cloud Web UI, the [Temporal CLI Cloud extension](/cli/cloud), the [Cloud Ops API](/ops), or the [Terraform provider](/cloud/terraform-provider).
[Pricing](/cloud/pricing) for Azure Namespaces is the same as for AWS and GCP.

Azure Public Preview differs from the standard [Public Preview](/evaluate/product-release-stages#public-preview) stage in two ways:

- **Access is gated.** Azure regions are enabled per account after a capacity review, rather than being available to everyone.
- **The SLA applies.** The [Temporal Cloud SLA](https://temporal.io/sla) covers Azure Namespaces during Public Preview.

### Azure functionality differences

- **CLI:** `tcld` does not support Azure Namespace management. Use the [Temporal CLI Cloud extension](/cli/cloud) instead.
- **Private Link service aliases:** Aliases are account-specific and provided by Temporal Dev Success. They are not published and cannot be retrieved programmatically through the Cloud Ops API, Temporal CLI, or Terraform. See [Azure Private Link](/cloud/connectivity/azure-connectivity).
- **Audit Logs:** An Azure-native streaming sink is not available. Audit events for Azure are included in the overall audit log, and can be accessed via the [Web UI](/cloud/audit-logs), [Cloud Ops API](/ops), or streamed to your existing [AWS Kinesis or GCP Pub/Sub sink](/cloud/audit-logs#configure-audit-logs).
